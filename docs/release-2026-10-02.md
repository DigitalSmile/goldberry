# The first Release run, `v2026.2`

Working notes for 2026-10-02. The tag `v2026.2` on 190569a5 started Release run
36985188261, the first run of `release.yml` on a tag. It went red in one test on
one lane. `maven` needs every lane, so nothing was uploaded to Central. The
`notes` job had already opened the draft GitHub Release, and that job edits a
draft that already exists, so running it again is safe. No ADR: the fix is to a
test and decides nothing.

Status legend: **done** — fixed and green locally; **confirm** — waiting on CI.

## 1. What was red

| Job | Step | Failing tests |
|---|---|---|
| `publish / windows / Java` | `build -Pgoldberry.skipNative=true` | `:media:testWithoutGpu` 1 of 720: `HttpIO > a server that answers Range > a read waits no longer than the source's timeout` |

Every other job that had finished was green: the Java lanes on Linux and macOS,
the four `FFmpeg and :media` jobs, three `libgoldberry` builds and their `Verify
layouts` jobs. When the run was read, `libgoldberry (windows-x64)` was still
building.

## 2. The failure

| Failure | Where | Cause | Fix | Status |
|---|---|---|---|---|
| `HttpTimeoutException: request timed out` from `HttpClientImpl.send` in `HttpIO.request`, called from `HttpIO.open` | `HttpIOTest$Ranged.timesOut`, Windows Java lane | the test gave the source a 300 ms timeout, which `HttpIO` also uses for the open request's headers. With PMD running alongside, the Windows runner took longer than that to answer on loopback, so the open failed and the read was never reached. The Snapshot run on the same commit passed it | the source's timeout is 2 s, enough for a loaded runner to open. The test now times the read: at least the timeout, and less than 10 s, well short of the 30 s stall timeout and the server's 30 s stall. Before, it only checked which exception came back | **done** — 26 of 26 `HttpIOTest` tests green, the read times out in 2.04 s; Windows **confirm** |

## 3. Getting the release out

The tagged code is the same: only a test changed. Two ways to go on:

- **Re-run the failed jobs** of run 36985188261 once it has finished. That
  re-runs `publish / windows / Java` and the jobs waiting on it (`maven`,
  `bump`) on the same tag. The flaky test is as likely to pass as it was in the
  Snapshot run.
- **Move the tag** to a commit that has the fix (delete `v2026.2`, tag again,
  push). A new run starts from the beginning, and the draft release is edited
  rather than created again.
