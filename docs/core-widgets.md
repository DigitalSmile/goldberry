# Goldberry — Core Widgets

Companion to `ARCHITECTURE.md` §11. Specifies every built-in widget.

**Where they live.** Every widget in this document is in the single
`goldberry-widgets` module ([ADR-0014](../book/src/adr/0014-single-widgets-module.md)),
separated by *package* and not by artifact under
`io.github.digitalsmile.goldberry.widgets.*`
([ADR-0091](../book/src/adr/0091-one-module-a-package-per-control.md)) — the
table below is that package layout.

`:core` holds **no widgets at all**. It holds the machinery they are built from —
`Widget`, `Element`, `Attributes`, the cascade, layout, text and paint — and for a
while it also shipped `row`, `column`, `text`, `panel` and `spacer`, because the
engines needed something to prove the widget tree against before there was a
catalog to prove it with. Once there was one, those five were the only widgets in
a module that is not a widget toolkit, and they moved
([ADR-0092](../book/src/adr/0092-a-primitive-is-a-widget-like-any-other.md)).

Inside a group there is **one package per widget**, holding it and its parts —
`…controls.slider` is `Slider` plus its nine — so a part stays package-private
and unreachable from anywhere but its own control, which is what makes
"CSS-selectable and not constructible" a rule the compiler keeps.

| Package      | Contents |
|--------------|----------|
| `core`       | layout & primitives: `row`, `column`, `stack`, `spacer`, `scroll`, `canvas`, `image`, `icon`, `focus-scope`, `affix` |
| `text`       | `text` (+ inline `span` runs), `link` |
| `controls`   | `button`, `toggle`, `checkbox`, `radio`/`radio-group`, `slider`/`fader`, `knob`, `select`, `segmented`, `progress`, `spinner`, `badge` |
| `form`       | `form`, `field`, `text-input`, `text-area`, `date-picker`, `time-picker`, `color-picker`, `code-input`, autocomplete, validation model |
| `panel`      | `panel`, `card`, `group-box`, `tabs`, `split-pane`, `collapse`, `carousel`, `statistic`, `skeleton` |
| `nav`        | `breadcrumbs`, `steps`, `wizard` |
| `overlay`    | `dialog`, `toast`, `tooltip`, `popover`, `message`, `tour` |
| `menu`       | `menubar`, `menu`, `item`, `separator`, context-menu attachment |
| `shell`      | `tray-icon`, `titlebar` (CSD), window chrome |
| `collection` | `list`, `tree`, `calendar`, `timeline`, `table` (deferred) |

`nav` is the one package added since v0.1's nine. `breadcrumbs`, `steps` and
`wizard` all answer "where am I in a sequence", which is neither a surface
(`panel`) nor a control that reports a value (`controls`); folding them into
either would have made that package's name a lie. Principle 3 in
`design-system.md` §1.1: extend deliberately, do not improvise.

**Status.** Everything below is a specification. `design-system.md` §5 requires a
spec *and* a §3 metrics row *and* gallery coverage before code, in that order —
so a widget appearing here has passed the first two gates and not the third.
`book/src/status.md` tracks which are built.

**The widget contract** (every widget in this document):

- **KDL node name = CSS type selector = registry name.** `button` in markup, `button { }` in CSS, `Button` record in Java. Parity enforced by test.
- **States are pseudo-classes:** `:hover :active :focus :focus-visible :disabled :checked` (plus `:invalid` for form controls — an addition to the CSS engine's pseudo set, **made** in ADR-0169).
- **Colors and metrics only via `--gb-*` tokens** — no literal colors in widget painters; themes restyle everything.
- **Semantics:** every widget populates the semantics tree (role, name, value, state, actions) — noted per widget below.
- Disabled state propagates down the tree; a disabled container disables its descendants for input and semantics.

---

## 1. `widget.core` — layout & primitives

- **`row` / `column`** — flex containers (direction preset); all Yoga properties via CSS or attributes (`gap`, `justify`, `align`). No intrinsic painting. Semantics: generic group.
- **`stack`** — z-order layering; children positioned by alignment or absolute insets. Basis for badges-over-things and custom overlays. **Built** ([ADR-0250](../book/src/adr/0250-a-stack-is-one-child-in-flow.md)), and it is nine lines because it positions nothing: the **first child stays in flow** so the stack has a size and wrapping an existing widget in one cannot move it, and every child after it is `position: absolute` so an overlay cannot resize what it sits on. Both halves of "alignment or absolute insets" already worked — an absolute child with no inset is placed by the container's `align-items`/`justify-content` and its own `align-self` ([ADR-0244](../book/src/adr/0244-a-child-may-say-where-it-sits.md)), and one with an inset goes where it says. Z-order is document order.
- **`spacer`** — `flex-grow: 1` shorthand widget.
- **`scroll`** — one or both axes; overlay scrollbars per the design-system spec (thin, hover-widening, fade when idle); pixel-precise wheel with line fallback; keyboard (PgUp/PgDn/Home/End/arrows when focused); `scrollIntoView(widget)` API; scroll position is retained state surviving rebuilds. Repaint boundary by definition. Semantics: scrollable region with scroll actions.
- **`canvas`** — immediate-mode Blend2D painting surface: `onPaint(ctx, size)` called on invalidation; `invalidate()` to request repaint; hit-testable; the substrate for charts, meters, and app custom drawing. Escape hatch by design.
- **`image`** — sources: path, classpath, bytes, or async supplier (placeholder fill until loaded); fit modes `contain | cover | fill | none`; DPI-aware (picks raster scale by physical pixels); Blend2D codecs (PNG/JPEG/QOI); `image/svg+xml` routes to `goldberry-vector` when present. Semantics: image with alt text (required attribute for non-decorative use).
- **`icon`** — Lucide registry by name; sized in `em` (follows `font-size`) or explicit px; tinted by CSS `color`; app icon packs registrable. Decorative by default in semantics unless labeled.
- **`focus-scope`** — traversal boundary: contains Tab order, optional `autofocus` target, focus restoration on scope exit (dialogs and popovers wrap one automatically).
- **`affix`** — pins its single child to an edge of the nearest `scroll` once the child would have scrolled past it: `edge="top|bottom|left|right"`, `offset` in px. The child keeps its place in layout — `affix` leaves a same-sized hole behind, so nothing below it jumps when it detaches. `:affixed` is a pseudo-class, so a sticky header can gain a shadow the moment it lifts. Not `position: sticky`: §8's CSS subset has no `position` at all, and this is a widget precisely so the subset does not have to grow one. Semantics: transparent — it adds no role, it only moves its child.

```kdl
row gap=8 class="toolbar" {
  icon name="search"
  spacer
  button icon="plus" "New"
}
```

## 2. `widget.text`

- **`text`** — the single text-display widget. Typography via token styles (`style="title"` → the §10.1 scale) or CSS font properties. Wrapping on by default; `wrap=#false`, `ellipsis` (end-truncation with … when constrained), `max-lines`. Alignment `start|center|end`.
- **Inline styled runs:** child `span` nodes carry class/style for mixed formatting inside one paragraph; spans may nest one level. Links inside text = `span class="link" action="…"`.
- **`link`** — text that does something. `action="…"` for in-app navigation or `href="…"` for an external target opened through the platform; `visited=#true` is the application's to set, because the toolkit keeps no history. Focusable and in the Tab order (unlike `text`), `Enter` activates, `:hover` underlines, `:focus-visible` takes the standard ring. External links carry a trailing 12px `external-link` icon and their accessible name says so, because "opens outside this window" is not something a colour can convey. A `link` inside a paragraph is the block-level spelling of `span class="link"`; the `span` form stays for mid-sentence use and shares the styling. Semantics: link, with `href` or the action name as its target.
- Selection/copy for static text: deferred to the text-editing depth milestone (ARCHITECTURE §17) — same machinery, one implementation.
- Semantics: text content verbatim; heading level inferred from typography token (`title`/`heading` → heading roles).

```kdl
text style="body" {
  span "Goldberry is "
  span class="b" "fast"
  span " and themable."
}
```

## 3. `widget.controls`

All controls: focusable, full keyboard operation, `:focus-visible` ring per the design system, semantics role + state, value changes raised as events and through `bind`.

- **`button`** — variants via class: `primary | secondary (default) | ghost | danger | link`, plus **`outlined`** (transparent fill, 1px `--gb-border`, text in `--gb-text`; composes with the semantic variants, so `button.outlined.danger` is a danger outline). Shape via class: default radius 8, **`square`** for radius 0 where buttons butt against each other or against a field, and **`circle`** for a `full` radius. **A button given an icon and no label is a circle by default** — an icon-only button is a disc everywhere else in the canon, and requiring `class="circle"` to get the obvious result is the kind of improvisation Principle 3 exists to prevent; `class="square"` overrides it. Icon-only buttons still require an accessible name (§1.6), which is the `aria-label`-equivalent attribute `name=`.
  **`float=#true`** lifts the button out of layout and pins it to a window corner — the floating action button — at `--gb-window-margin` from both edges, `corner="bottom-end"` by default, elevation 1. It is a class of *placement*, not of appearance, so it composes with every variant and shape above; a floating button that is not `circle` is legal and unusual.
  **`link`** is a button that reads as running text: transparent fill, the theme's link ink, `body` weight and 4px of horizontal padding, with `ghost`'s overlay wash on hover. It is a *button* — in the tab order, focus ring, `Space` and `Enter` — and it is **not** §2's `link` widget, which is a word inside a sentence and needs an underline that §8's subset cannot yet express. **Built** ([ADR-0293](../book/src/adr/0293-a-button-that-reads-as-a-link.md)); `outlined`, `square`, `circle` and `float` are not.
  Content = label, icon, or both; `Space/Enter` activates; `default=#true` (Enter in dialog) and `cancel=#true` (Esc) roles. Semantics: button.
- **`toggle`** — switch; drag or click/Space. Semantics: switch.
- **`checkbox`** — binary or tri-state (`indeterminate`); label is part of the widget (click target includes label). Semantics: checkbox with mixed state.
- **`radio` / `radio-group`** — group is the focusable unit; arrow keys move selection (roving focus); exactly-one invariant held by the group. Semantics: radiogroup/radio.
- **`slider`** — horizontal default; `min/max/step`, optional tick marks and value label; keyboard arrows (step), PgUp/PgDn (large step), Home/End; **`fader`** = vertical variant with optional dB scale mapping. Semantics: slider with value text.
- **`knob`** — rotary: vertical-drag primary (circular-drag optional), wheel steps, keyboard arrows, modifier for fine adjustment, optional detents, `min/max`, arc indicator, and a **pointer** on the dial saying which way it is turned. **Clicking the ring positions the value** at the angle clicked (the ring is a track); clicking the dial grabs it for a drag and does not jump. Semantics: slider.
- **`select`** — closed control + popup list (backend popup window, so it escapes window bounds); typeahead; keyboard open (Space/Alt+Down), arrows, Enter/Esc. Option model or inline KDL `option` children. `multiple=#true` renders the selection as `badge` chips inside the closed control, each with a remove affordance. **Built, in its v1 form** ([ADR-0141](../book/src/adr/0141-a-select-is-a-closed-control-and-a-list.md)): the closed field, the popup list, inline `option` children — the same record `segmented` writes, which moved to a package of its own the day it had two callers — and typeahead on the closed control. The control **opens itself**, which is the part that had to wait: opening needs a window, and a widget had no way to reach one until `BuildContext.host()` ([ADR-0140](../book/src/adr/0140-a-widget-may-reach-its-window.md)) — a `menu` is still opened by the application, because a menu bar genuinely is an application's, and a dropdown is not. **Arrows move and `Enter` chooses**, which is this line's own words and the opposite of `segmented`'s roving selection; the shared `option` carries which of the two it is in. **`multiple=#true` is built** ([ADR-0182](../book/src/adr/0182-a-select-may-hold-more-than-one.md)): the selection is a set, drawn as `badge` chips in the closed control with a × on each, and `change` is a **toggle** in that mode — the set is the application's, so asking for a value it already holds can only mean taking it out, which is what keeps a chip's × and a click on a chosen row from being two ways of saying one thing. The list stays open while values are picked, which needed a popup whose content can change while it is open. **`autocomplete=#true` is built** ([ADR-0183](../book/src/adr/0183-a-combobox-is-a-select-you-can-type-in.md)): the closed control holds a real `text-input` — literally the one §3 names, so the editing model, the undo history, the clipboard and the caret stay where their rules already live — the field stops being a Tab stop and delegates focus so a combobox is one stop, `Space` types a space rather than opening, and `Esc`-restores plus the refusal of a free-typed value both fall out of one nullable string of offered text that `TextInputState.follow` already knew how to honour. **`tree=#true` is built** ([ADR-0184](../book/src/adr/0184-a-tree-is-a-list-that-remembers-what-is-open.md)): the popup is a `tree` over the application's node model, leaf-only by default, and the closed control is unchanged. What is not built: typeahead inside the open list, which needs a text capture phase the router does not have; and a width that follows the widest option rather than the current value. All are in `book/src/TODO.md`.
  **`autocomplete=#true`** makes the closed control an editable `text-input`: typing filters the options, the popup stays open and narrows, `Esc` restores the last committed value rather than clearing, and a free-typed value is refused unless `free=#true`. The distinction that matters is that filtering is the *application's*: `select` raises the query and renders whatever options it is handed back, so a remote-backed autocomplete is the same widget with a slower model. Semantics: combobox, editable when `autocomplete`.
  **`tree=#true`** takes a `tree`'s model instead of a flat option list, so the popup is a `tree` and a selection is a node. Selecting a parent is `checkable="leaf|any|cascade"` — leaf-only by default, because "Europe" is usually a heading and not an answer. Semantics: combobox owning a tree.
- **`segmented`** — a row of mutually exclusive options rendered as one bar, sharing `radio-group`'s model and invariant exactly: one Tab stop, arrows rove, exactly one selected, `change` reports the value. **The arrows are `Left`/`Right` only**, unlike a radio group's: a bar has an axis of its own where a group's is its stylesheet's, so `Up`/`Down` stay with whatever is above it ([ADR-0078](../book/src/adr/0078-a-focus-scope-has-an-axis.md)). It is `radio-group` with a different drawing, and it is a separate widget rather than `radio-group.segmented` because the two are not substitutable in a layout — a segmented control is a fixed-width bar that belongs in a toolbar, a radio group is a list that belongs in a form. Options are inline `option` children with a label, an icon, or both; icon-only segments require `name=`. **Segments are equal width** — each exactly 1/n of the bar, which is what lets the selection indicator travel between them rather than fade in place; the bar therefore takes the width it is given and fills its parent when nothing gives it one ([ADR-0099](../book/src/adr/0099-an-indicator-travels-on-a-grid.md)). Semantics: radiogroup/radio.
- **`progress`** — determinate (`value/max`) and indeterminate (animated, reduced-motion aware). Semantics: progressbar.
- **`spinner`** — small indeterminate activity indicator. Decorative in semantics unless labeled.
- **`badge`** — count/status chip, typically composed inside `stack`. Semantics: text.

## 4. `widget.form`

- **`form` / `field`** — layout contract: consistent label column (or stacked labels via class), required marker, control slot, message slot below. `field` wires label→control for semantics and click-to-focus automatically. **Built** ([ADR-0169](../book/src/adr/0169-a-field-is-silent-until-you-leave-it.md)), with two departures worth stating. **Stacked is the default and the column is `field.horizontal`**, because the column is the form that needs a number — every label has to be the same width and §8's subset cannot say "as wide as the widest of these", so a default label column would be a default that is wrong until configured. **Click-to-focus is built** ([ADR-0170](../book/src/adr/0170-a-document-names-an-object-and-a-label-hands-focus-down.md)) through `Handles.delegatesFocus()`, which turns the router's walk round: a press that finds no focusable ancestor takes the first focusable *descendant* of a container that claims one, which is what a label needs because a label is its control's **sibling** rather than its parent. Semantics wait on the AccessKit bridge (M5) like everything else's. A form is also where the **label column** is decided — `form.horizontal`, with `field.horizontal` for a field standing on its own and `form.horizontal field.vertical` for the one that wants the width back. A field is **two boxes**, not four: a label column is a *row* and a message below is a *column*, and §8's subset has no grid, so the shape comes from the tree — `field-label` beside `field-body`, and the body is always a column holding the control and the message. An **action row is a `field` with no label**, which is what lines a Save button up with the controls rather than with the labels.
- **`text-input`** — single line. v1 scope: caret, selection (mouse+keyboard+word ops), clipboard, undo/redo stack, placeholder, max-length, `password` mode (masking, no clipboard-out), input filters (numeric etc.). ~~IME preedit~~ and RTL editing deferred (ARCHITECTURE §17) — **IME preedit landed** ([ADR-0292](../book/src/adr/0292-a-field-composes-and-a-password-does-not.md)): a composition is drawn underlined at the caret with its converting clause highlighted, held beside the value rather than in it, so `change=` fires once for the accepted candidate and not once per keystroke of a string that is about to be replaced. A `password` **refuses** to compose, because a candidate window is a second, unmasked window showing what is being typed — which is what Windows and macOS do with their own secure fields. Semantics: textbox. **Built, and all of that v1 scope is in it** ([ADR-0167](../book/src/adr/0167-a-field-owns-its-caret-and-the-model-is-told.md)): the field owns the edit and reports each value through `change=`, because a caret, a selection and an undo stack are not things a model can hold — a `bind=` value is the initial text and an override, and the field ignores the echo of the user's own keystroke rather than resetting the caret on every letter. The editing rules are a **value** (`TextEdit`), so every one of them is tested with no font, no frame and no window, and undo is a stack of states rather than a log of inverse operations; a run of keystrokes is one `Ctrl+Z` by one rule — this change starts where the last one ended — from which "a caret move breaks the run" and "a click breaks it" both fall out. The caret is drawn from `Paragraph`'s two new measurements and blinks on a **timer rather than the frame clock**, because a caret changes twice a second and `isAnimating` would run the loop at the display's rate for as long as a form was open. Two facilities had to be built underneath it: the **clipboard**, which was the SPI's last named hole, and **`SDL_StartTextInput`**, which nothing had ever called — so committed text had never once arrived on a real SDL window.
- **`text-area`** — multi-line: soft wrap, optional auto-grow between min/max rows, scrollbar beyond. Same editing scope as `text-input`. **Built** ([ADR-0171](../book/src/adr/0171-a-column-is-an-x-and-a-width-arrives-late.md)): the editing model, the undo history, the clipboard and the caret's blink are `text-input`'s, unchanged — what a second dimension adds is `Enter`, vertical movement, a selection that is **one rectangle per visual line**, and a control that sizes itself. The three parts are shared rather than copied, in a package the module does not export, so there is one `text-caret` rather than two kept alike by hand. The one piece of state a second dimension needs is the **preferred column**: `Up` keeps the column, a column is an *x* rather than an offset, and a run of them has to survive a short line in the middle. The height is the widget's and not the stylesheet's, because it is a function of how many lines the text wrapped into and no selector can ask that. *Not built: a visible scrollbar — it scrolls with the wheel and to keep the caret in view, and `scroll`'s bars are a viewport's rather than a control's.*
- **Validation model** — `Validator<T>` per field; run on blur and on submit (configurable); failures set `:invalid`, render the message slot in `--gb-danger`, and register in the form's error summary. `form.submit()` gates on validity and raises a typed event with bound values. **Built** ([ADR-0169](../book/src/adr/0169-a-field-is-silent-until-you-leave-it.md)): a validator returns a **message** rather than a boolean, because a field that goes red without saying why is one somebody has to guess at, and `and` reports the first failure because a message slot is one line. Blur is `Handles.onFocusWithin` — the notification `:focus-within` would be — which reports the *subtree*, so a field holding three controls behaves like a field holding one. A field is **silent until it has been left once and live from then on**, which is in no specification and is what every good form does. `:invalid` is a real pseudo-class, which is what §1's list asks for. **`submit` carries nothing**, and that is the departure: `bind=` reads *from* the application's model, so an event carrying the bound values would hand an application its own data back — and `binding()` is an `Observable` rather than a path, so the toolkit could not name them. A `FormController` is what submits, because a Save button is usually outside the form — and a **document names one**, through the `Named` registry that also resolves `validator=` ([ADR-0170](../book/src/adr/0170-a-document-names-an-object-and-a-label-hands-focus-down.md)). That registry is the fourth, and it exists because the other three each refused the job: an action is a method, an icon is a resource with a lifetime, and a binding is a value that *changes* — which the binding machinery says out loud, refusing a `final` `@Bind` field with "a value that cannot change is not something to subscribe to".
- **`date-picker` / `time-picker`** — a `text-input` that parses, plus a `popover` holding a `calendar` (date) or an hour/minute/second column set (time). `date-picker range=#true` selects a pair and reports it as one value. The **typed field is the source of truth**, not the popup: a date picker you cannot type into is unusable for a birthday, and every keyboard user reaches the field before the grid. Parsing and formatting take a `java.time` formatter the application supplies, defaulting to the locale's short form — the toolkit does not invent a date syntax. Value type is `LocalDate` / `LocalTime` / `LocalDateTime`; `min`, `max` and a `disabled` predicate gate both the field and the grid, so an unreachable date cannot be typed either. Keyboard: `Alt+Down` opens, arrows move within the grid, `PgUp`/`PgDn` change month, `Esc` reverts. Semantics: combobox owning a grid, with the formatted date as its value text. **Both are built** ([ADR-0274](../book/src/adr/0274-a-calendar-is-told-what-day-it-is.md), [ADR-0275](../book/src/adr/0275-a-wheel-is-a-column-that-wraps.md)), and they are one control with different things in the popover — the field, the affordance, `Alt+Down`, `Esc` and the delegated focus are one shared node. A time's popover is a **wheel** per column: five rows centred on the value, wrapping at both ends, which is what every platform's own time picker does and what avoids a `scroll`, a controller and a `Located` cell per column. The wrap is what makes the quiet neighbours honest — `58 59 00 01 02` says what comes next where a list clamped at 59 would stop. Its **arrows split by axis** where a calendar's do not: `Up`/`Down` turn a wheel and `Left`/`Right` choose which, so this row's "arrows move within the grid" means two different things for the two pickers. A `time-picker`'s wheels **report on every turn**, unlike a calendar's roving day, because there is no unchosen state for an hour. `precision=` is the one option not in this row: §4 names three columns and every clock shows two, so it is which of them a picker has, and the default format follows it — `FormatStyle.SHORT` is never seconds. The field is a real `text-input` and the popover holds §10's `calendar` unchanged, so the picker configures a month rather than reimplementing one. **The text is the state and the date is derived**, which is this row's own first sentence built rather than quoted: holding a `LocalDate` and rendering it into the field has to answer what the field says while somebody is halfway through typing, and every answer to that either fights the caret or eats characters. The grid **writes text into the field**, exactly as a user would, so a value takes one path and is parsed in one place. `allows` is the single place `min`, `max` and the predicate are asked, by the grid that draws a day and by the field that parsed one — and a refused date is left *in the field* and simply not committed, because deleting what somebody typed is how a field loses a keystroke they were halfway through. Three departures worth stating. **The month is an argument**: nothing in the catalog may read the machine's time zone (ADR-0203), so a picker that opened on "this month" would be deciding what month it is — and `today` may be null, which marks no day rather than guessing at one. **A range's separator is the one date syntax the toolkit writes**, an en dash with spaces, because no locale service answers "how does this language join two dates"; parsing accepts a plain hyphen too, which is why the separator cannot *be* a bare hyphen. And **a document's `change` carries the formatted text where Java's carries the value**, because §9's valued actions cross as a `String`. The typed-value seam this row implied is `Validator.parsing`, and `field` needed no change to take it. *Not built: `time-picker`, and the value text half of the semantics line — `Semantics` has no channel for it, for any widget (M5).*
- **`color-picker`** — a swatch button opening a `popover` with a saturation/value plane, a hue slider, an optional alpha slider, a hex `text-input`, and an application-supplied palette of preset swatches. The hex field is the source of truth for the same reason the date field is. Value is the toolkit's `CssColor`, so a picked colour is directly usable in a stylesheet; the model carries OKLCH internally because that is what §1.7 interpolates in and what the ramp utility uses, and round-trips to hex without drift. `alpha=#false` (the default) hides the alpha slider and refuses translucent values. Keyboard: arrows move the plane cursor by 1, `Shift`+arrows by 10. Semantics: combobox with the hex as its value text — a colour name is not something the toolkit can honestly produce. **Built** ([ADR-0276](../book/src/adr/0276-a-plane-is-hsv-and-the-hex-is-the-value.md)), with **one departure** and it is the model. **The plane is HSV, not OKLCH.** A saturation/value plane *is* HSV — the axes are S and V — where OKLCH's are lightness, chroma and hue, and OKLCH chroma has a gamut boundary that varies with both of the others: a rectangular plane over it has large unreachable regions, a cursor that cannot be put where it was clicked, and a colour that changes when the hue slider moves under a stationary cursor. This row's stated reason for OKLCH — "that is what §1.7 interpolates in" — is about *transitions*, and those still go through `Oklch`; a picked colour is an ordinary `0xAARRGGBB` and fades like any other, because dragging is not a transition. "Round-trips to hex without drift" is kept and asserted over 4,096 colours. **Two pieces of state, and the second is the point**: the hex is the value, and an `HsvColor` is kept beside it because the conversion is lossy exactly where people drag — every colour with no saturation is a grey with no hue, so a picker that re-derived it would swing the hue slider to red at the left edge. The plane, the ramps and the presets all **write hex into the field**, so a value takes one path and is parsed in one place. `alpha=#false` refuses in **both** directions, because a picker with no way to change alpha must not report one. Everything it draws is painted rather than styled — §8's subset has no gradient — which is why it has five goldens: a plane painted black-then-white instead of white-then-black is a grey square that passes every assertion. *Not built: the value text half of the semantics line, which needs a channel `Semantics` has for no widget (M5) — and the plane's own role is `SLIDER`, which is the nearest true thing, because neither this enum nor ARIA has a word for a slider with two axes.*
- **`code-input`** — the one-time-code field: `length=6` separate single-character boxes over one value, `type="digits|alnum"`. It exists as its own widget rather than a styled `text-input` because its *editing model* is different, and that is the whole of the specification: typing advances, `Backspace` on an empty box moves back and clears the previous one, **a paste of the full code fills every box at once** (the thing users actually do), and focus lands wherever the first empty box is. `complete` fires when the last box fills, which is what lets a form submit without a button. `mask=#true` for authenticator-style secrecy. Semantics: a single textbox with the whole code as its value — six boxes are a drawing, not six fields, and announcing them separately would be a lie. **Built** ([ADR-0273](../book/src/adr/0273-a-code-is-a-string-and-the-boxes-are-a-drawing.md)), and the paragraph's four editing sentences turned out to be two rules seen from four directions. `CodeEdit` is a **string and a box count** — no caret, no anchor, no undo stack, no per-box array — and the active box is `min(filled, length - 1)`, *derived* rather than held. So "focus lands wherever the first empty box is" is not implemented at all: it is what the derivation says on every frame, with nothing to keep in step. "Typing advances" and "a paste fills every box at once" are one append, because committed text arrives as a string either way. And `Backspace` has no second case — the box the ring is on is always empty, so the box to clear is always the one before it. **There are no holes**, which this paragraph's own last sentence requires: a code announced as one textbox cannot hold `12` and `56` with a gap between them, because that has no honest value. One departure worth stating: `CodeType` filters **per character and drops** what it does not want, which is the opposite of `TextFilter`'s reject-don't-correct rule — there is no caret for a correction to disturb, and a whole-value filter rejects a paste of `123 456` outright, which is the paste this widget exists for. `complete` fires on the edit that filled the last box and not on every rebuild of a full field, so a form does not submit twice. *Not built: arrow keys, and copy or cut — the first because there is one insertion point for them to move between, the second because §4 asks for no way out and a masked code must not have one.*
- **Autocomplete** — `text-input autocomplete=#true` attaches a `popover` of suggestions to the field: the widget raises the query, the application supplies the list, and the field's text is never rewritten without the user choosing. See `select autocomplete` for the combobox form; this is the free-text one, where the suggestions are a convenience and any value is legal. **Built** ([ADR-0182](../book/src/adr/0182-a-select-may-hold-more-than-one.md)) as `TextInput.suggesting(options)`, and all three of those sentences fall out of the shape rather than being enforced: the field reports what was typed through `change`, is handed a list back by being rebuilt, and reports a chosen suggestion through the same `change` — it sets nothing. The panel is the `select`'s list, and `Option.inAList()` is what makes it right here: the arrows move the focus and `Enter` commits, where follow-the-focus would rewrite the field under a user who is only looking. **Java-only in v1**: the list arrives by rebuilding the widget, which is a channel a document does not have.
- **Binding** — all form controls accept `bind="model.path"` against the observable `Property<T>` model (two-way).

```kdl
form {
  field label="Name" required=#true {
    text-input bind="user.name" placeholder="Jane Doe"
  }
  field label="Bio" { text-area bind="user.bio" rows=4 }
  row class="actions" { spacer; button class="primary" default=#true "Save" }
}
```

## 5. `widget.panel`

- **`panel`** — plain surface: `--gb-surface`, border, radius tokens. The building block; no elevation. **Built** ([ADR-0166](../book/src/adr/0166-a-raised-thing-is-told-apart-by-its-edge.md)) — and the rule was missing for a long time, which is how it was found: the widget drew nothing at all, so every document that wanted a surface invented one, and the showcase invented one that looked exactly like a `card`.
- **`card`** — elevated surface: shadow tokens, hover-elevation optional via class. Semantics: group with optional label. **Built** ([ADR-0164](../book/src/adr/0164-elevation-is-an-edge-and-a-closed-section-is-absent.md), [ADR-0166](../book/src/adr/0166-a-raised-thing-is-told-apart-by-its-edge.md)), and the elevation is an **edge**: §10's subset has no `box-shadow` and nothing here paints outside a box's own rectangle. The fill is `--gb-surface-raised` and the edge is `--gb-border-strong`, both of which say what they mean — `--gb-surface-2` was the first answer and is not an elevation at all, being a step *down* from `--gb-surface` on the light theme, where a card built on it read as recessed. The edge is an alpha over whatever is underneath, so it lightens on dark and darkens on light and stays right on a card sitting on a page, on a panel, or on another card. `class="interactive"` is the optional hover-elevation, opt-in because a card that lit up under the pointer would promise it does something. It carries no title: that line's "optional label" is the *accessible* name, which arrives with AccessKit in M5.
- **`group-box`** — titled border group for settings clusters. **Built** ([ADR-0166](../book/src/adr/0166-a-raised-thing-is-told-apart-by-its-edge.md)), with the frame round **both** the title and the content: the title is a header row inside the border, tinted and ruled off from the body. A `fieldset`'s legend *through* the border is still not available — it needs a notch the subset cannot express — and the first cut put the title *above* the frame instead, which was reported as "what is the purpose of group box?" and was the right question to ask of it: a heading floating over a bordered box is a heading and a `panel`.
- **`tabs`** — top placement v1; keyboard (arrows between tabs, Tab into content); closable tabs optional; lazy content instantiation; selected tab is retained state. Semantics: tablist/tab/tabpanel. **Built** ([ADR-0107](../book/src/adr/0107-a-tab-strip-is-a-model-a-header-and-a-panel.md)), with **adding and removing needing no API at all**: the strip reads the selection through `bind` and reports `change`, `close` and `new`, and the application answers all three — a strip whose `close` does nothing keeps its tab. A `tab` takes a label, an icon, `closable=#true`, and a **`colour=`** of its own, which is the one place a widget in this catalog takes a colour as data: a tab coloured after the project it belongs to is application data, and there is no selector for "the tab whose project is red". It is written through `restyle`, so the stylesheet still decides what it means — the label and the underline. Content is lazy by omission: only the selected tab's widgets are ever built, so a tab's content is **rebuilt when it is selected again** and anything that must survive belongs in the model. One Tab stop, arrows roving; the × is deliberately not focusable (nine tabs would be nineteen stops) and `Delete` is the keyboard's way to close one. **Tabs arrive and depart on the frame clock** — opacity and a small translation over §1.7's `base`, removed entirely under reduced motion — which cannot be a transition, because an arriving tab's element did not exist last frame and a departing one has already been dropped from the application's list ([ADR-0109](../book/src/adr/0109-a-tab-arrives-and-departs-on-the-frame-clock.md)).
- **`split-pane`** — two children, draggable divider (keyboard-resizable when focused), min sizes, optional collapse-to-edge; divider position retained. Semantics: separator with value. **Built** ([ADR-0165](../book/src/adr/0165-a-divider-translates-and-a-rotation-has-three-brakes.md)). The divider is a **translation**, not a position: the pointer is somewhere inside a six-point bar, and mapping that to a fraction would snap the divider so its centre jumped under the finger on every press — so it reports a `gestureAnchor` and the new offset is `anchor + dragX`, which is `knob`'s mechanism reached for a different reason. The position is a **fraction** so it survives a resize; the minimums are **pixels**, because "this list needs 160 points" is a fact about content. The first pane is given an explicit size and the second grows, because `flex-grow` shares out the space *left over* after content and would therefore ignore the divider's own fraction. The divider is the only tab stop: arrows along the axis step it, `Home`/`End` go to the minimums, and `Enter` collapses and restores when `collapsible=#true`. A collapsed pane is still **built** — collapse-to-edge is a size, not an absence, which is the opposite of `collapse`.
- **`collapse`** — a header and a body that folds away. `open` is retained state; `accordion=#true` on a containing `column` makes siblings mutually exclusive. **Built, `accordion` included** ([ADR-0164](../book/src/adr/0164-elevation-is-an-edge-and-a-closed-section-is-absent.md), [ADR-0166](../book/src/adr/0166-a-raised-thing-is-told-apart-by-its-edge.md)). `accordion=#true` **inflates to an `Accordion`**, which reports `column` as its own CSS type: the flag belongs on the container because "one open at a time" is a rule about siblings, but honouring it needs state and `column` is the most-used container in the toolkit — so a document writes what this line says and an ordinary column pays nothing. The body **arrives** on the frame clock (opacity and a small translation); closing is instant, which is asymmetric on purpose, because holding the subtree alive for the length of a fade is what this widget exists not to do. The header is one Tab stop, `Enter`/`Space` toggles, `Left`/`Right` close and open. **The body is unmounted while closed, not hidden**: a collapsed section that kept a live subtree would keep its subscriptions, its images and its scroll position alive for content nobody can see, and "cheap to rebuild" is what the widget tree is for (ADR-0004). The chevron rotates on `base`; the body does not animate its height, because height is not on §1.7's whitelist and never will be. Semantics: disclosure button plus region.
- **`carousel`** — one child visible at a time out of a list, with previous/next controls and a dot indicator. `loop=#false` by default. **Nothing advances on its own unless `interval` is set**, and when it is, the rotation pauses on hover, on focus anywhere inside, and entirely under reduced motion — §1.7 rule 4 says nothing loops except explicit continuous indicators, and a carousel that moves while being read is the canonical violation. Arrows move between slides when the strip is focused; slides are one Tab stop and their content is reachable inside. Semantics: a list with the current position announced. **Built, with one of the three pauses missing** ([ADR-0165](../book/src/adr/0165-a-divider-translates-and-a-rotation-has-three-brakes.md)). `interval` defaults to off and the rotation is one **one-shot** timer rescheduled after each slide, so that "pause" means "do not schedule the next" — and every reason to stop is re-checked when the timer *fires*, because a timer already in flight would otherwise advance one slide past the moment it should have stopped. Hover and reduced motion work completely. **Focus does not**: focus on the strip or the carousel's own controls pauses it, and focus on a widget *inside a slide* does not, because the cascade has no `:focus-within` and nothing tells a widget that focus landed in its subtree. Only the current slide is built, which is `tabs`'s bargain for `tabs`'s reason — and which is also why the move is an **arrival** and not a cross-fade: holding the outgoing slide alive for the length of one would be building a slide that has been moved away from. The arriving slide fades up with a small translation *from the direction of travel* ([ADR-0166](../book/src/adr/0166-a-raised-thing-is-told-apart-by-its-edge.md)), on the frame clock rather than as a transition, because a newly built element has no previous style to interpolate from. A dot is not focusable — nine slides would be nine tab stops on top of the two buttons.
- **`statistic`** — a labelled number: `value`, `label`, optional `unit`, optional `delta` with `direction="up|down"` rendered in `--gb-success`/`--gb-danger`, optional `sparkline` from a `canvas`. Formatting is the application's — the widget takes a string, for `slider`'s reason: a locale-aware number formatted inside the toolkit makes a golden image that cannot be reproduced on another machine. Semantics: text; the label and the value are one accessible name so they are never read apart. **Built except the sparkline** ([ADR-0164](../book/src/adr/0164-elevation-is-an-edge-and-a-closed-section-is-absent.md)), which waits on `canvas` and is one more child at the end of the column when it arrives. `direction` names the **sentiment** and not the arithmetic — latency falling is success — so the caller picks it and the widget never infers it from a leading `-`, which would colour a latency improvement red; and the colour is a class on the delta, so it stays the stylesheet's decision.
- **`skeleton`** — the placeholder a widget shows while its data loads: `shape="text|title|circle|rect"` and `lines` for the text form, sized from the typography token it stands in for so the layout does not jump when the real content arrives. **A shimmer is a loop**, so §1.7 rule 4 applies: it is a `linear` opacity pulse on `--gb-motion-overlay`×5, it is the only decoration in the canon allowed to loop, and under reduced motion it holds still at its dimmest. Semantics: `busy`, with no text — a skeleton announcing "loading" once per placeholder would announce it thirty times. **Built** ([ADR-0164](../book/src/adr/0164-elevation-is-an-edge-and-a-closed-section-is-absent.md)): the pulse is a pure function of the frame clock rather than a transition — a transition runs between two states and a skeleton has one — which is `spinner`'s arrangement (ADR-0081) and is why a row of them is in step by construction. A **triangle wave** folding at the halfway point, so the ends meet and it does not snap once a second; between 0.45 and 1.0, because a placeholder that fades to nothing flickers the layout empty and one at full strength is indistinguishable from content. The last line of a paragraph is short, since a block of identical full-width bars reads as a table rather than as prose.

## 6. `widget.nav`

Three widgets answering one question — where am I in a sequence — and sharing one
model: an ordered list of steps, a current index, and which of them are reachable.

- **`breadcrumbs`** — the path to here: `crumb` children with a label, an optional icon and an `action`; the last is the current page and is **not** a link. Overflow collapses the middle into a `…` that opens a `menu` of the hidden crumbs, rather than eliding characters — a truncated folder name is worse than a hidden one, because it looks like a name. Separator is a `chevron-right` icon in `--gb-text-muted`, not a character, so it never joins the text run. Semantics: navigation landmark containing links, current page marked.
- **`steps`** — a progress indicator over an ordered list: each step has a label, an optional description, and a state of `done | current | upcoming | error`. `direction="horizontal|vertical"`. Standalone it is a read-only picture of where a process is; `clickable=#true` raises a `change` for a step the application says is reachable, and refuses the rest — the widget never decides reachability itself, because only the application knows whether step 3 is valid yet. Semantics: a list with the current item marked; states are in each item's accessible name, since colour alone cannot carry `error`.
- **`wizard`** — `steps` plus a content area plus an action bar, which is the whole of it: it owns *no* validation, no navigation policy and no data. Back/Next/Finish raise events the application answers by moving the index, so a wizard that refuses to advance is an application that did not move it. `steps` is a child widget rather than a drawing, so a wizard's indicator is the standalone one and cannot drift from it. The content area is a `focus-scope`: advancing moves focus to the new step's first control, because a keyboard user who pressed Next and stayed on the button has not moved. Semantics: group with the step count and position; the action bar follows §2.3's platform button order like a dialog's.

## 7. `widget.overlay`

All overlays render in the in-window overlay layer or backend popup windows as appropriate; each wraps a `focus-scope` and restores focus on close.

**Restoring focus on close is built for the in-window half** ([ADR-0180](../book/src/adr/0180-the-keyboard-goes-back-where-it-was.md)): when a modal closes, the keyboard goes back to whatever had it before the modal opened, with its `:focus-visible` state intact. Underneath that was a bug nobody had looked for — `Element.unmount` tells the element tree and nothing else, so the router went on holding an element that had left it — and the fix is two rules, the first of which applies to every subtree that goes away rather than only to overlays. **The popup half needs no restoring**: a popup has its own tree and its own router and touches neither of the owner's, so a control that opened one keeps its focus and its ring for as long as it is up; only the platform's own window focus is still in question.

**The in-window layer exists** ([ADR-0100](../book/src/adr/0100-a-window-has-a-layer-above-its-application.md)): every window's tree is rooted at a `window-root` whose children are the application's root and whatever is floating over it, pinned to a `Corner` and out of flow, so an overlay takes no space from the content and is painted after it. `host.overlay(widget, corner)` puts one there and hands back the handle that removes it. The popup-window half of the SPI now exists as well ([ADR-0102](../book/src/adr/0102-a-popup-is-a-window-the-platform-may-refuse.md)): `Backend.createPopup` opens a real platform window parented to another and positioned in its coordinates, so a dropdown taller than the space below its button is not clipped to four of its nine options. It returns an `Optional`, because popup support belongs to the video driver — every desktop one has it — and the fallback for a driver without is this same in-window layer. **And the widget layer over it exists** ([ADR-0103](../book/src/adr/0103-a-popup-is-a-second-tree-in-a-second-window.md)): `host.popup(content, at, size)` puts a widget tree in that window — its own element tree, render tree and pointer router, painted by the *owner's* renderer so it is themed, restyled and animated by the same cascade and the same clock — anchored with `host.anchor(id)` to a node's painted rectangle, and light-dismissed by a press or `Escape` in the window below. The showcase's `Menu` button opens one. What `menu`, `tooltip`, `popover` and `select` still want is their own: placement that flips near a screen edge, sizing to content, focus travelling into the popup and back, and a submenu chain; `toast`, `dialog`'s scrim and `hud` want the in-window layer and not a second platform window.

- **`hud`** — the frame loop, on top of the window it is running: `fps` and `paint` by default, `frame` (the interval) on request, as `readings="fps frame paint"`. Each reading is a `hud-reading` part with its own class, so a stylesheet can dim the units or colour a paint time that has run out of budget. **It never asks for a frame**: a frame-rate display that requested one so it could show a fresh number would falsify §1.7's "the frame loop is fully idle when no animation is active" for every window with one in the corner, and would then be reporting a rate it had caused. So it reports the frames that were already happening — watch it during a resize or a drag — and on an idle window the numbers freeze with the loop. A HUD with no frame loop over it draws dashes rather than zeroes, because a zero is a measurement. Numbers are formatted in the root locale for §5's reason, which applies with more force here: these are the toolkit's own numbers. Decorative in semantics — a screen reader announcing a frame rate sixty times a second is not an accessibility feature ([ADR-0101](../book/src/adr/0101-a-diagnostic-must-not-be-the-thing-it-measures.md)).

- **`dialog`** — modal: scrim over the window, focus trap, `Esc` = cancel-role button, `Enter` = default-role button; **platform button order** (affirmative-right on macOS/Linux; theme-controlled) applied by the dialog's action bar automatically. Sizes to content with min/max. Semantics: dialog with labelled title. **Built** ([ADR-0176](../book/src/adr/0176-a-dialog-is-a-widget-and-showing-one-is-not.md)), with the split `menu` has: a dialog is a widget and `Dialogs.show(host, dialog)` is what puts one on a window, because a modal needs a window to cover and a widget has none. **Modality is two different things.** The pointer's is geometry — the scrim is a filling `Overlay`, which takes every press wherever it draws — and the keyboard's is a declaration, `Handles.isModal()`, which the router reads as "while something modal is mounted, the focused node is inside it". The roles are **values on the action** rather than classes, because `Esc`, `Enter` and the button order all need the dialog to know which button is which; two affirmatives is refused when the dialog is built. Both keys are on the **bubble** phase, so a `text-area` keeps `Enter` and an open `select` keeps `Esc`. The **order** is one declaration a theme owns — the bar writes neutral, dismissive, affirmative and a Windows theme reverses it — because `children()` runs before anything has asked the platform anything. **And `min/max` is built now** ([ADR-0181](../book/src/adr/0181-a-box-may-say-how-small-and-how-large.md)): §8's subset gained `min-width`, `max-width`, `min-height` and `max-height`, so "min width 320, max 80% of the window" is two declarations rather than a paragraph explaining why it is not. The 80% is a *percentage*, which is what lets a stylesheet say "of the window" without measuring one — a percentage resolves against the containing block and a dialog's is the scrim — and it is why the scrim now has no padding across it: with the padding, the maximum would have been 80% of the window less 48px, which squeezes a dialog below the width this line allows it.
- **`toast`** — non-modal notifications: queued, timeout with hover-pause, optional action button, stacking corner configurable; announced via semantics (live region) for future screen-reader bridging. **Built** ([ADR-0177](../book/src/adr/0177-a-toast-is-a-queue-and-the-stack-is-the-widget.md)), and it is the one widget in the catalog whose **value is not a widget**: a `Toast` is a record raised through a `ToastController`, because §7's own distinction — a message is part of the layout and a toast is a thing that happened — means nobody writes one anywhere. The **stack** is the widget, one per window in the corner overlay layer, and holding the list is what lets a toast outlive its own dismissal long enough to fade. "Queued" is read as a cap of three with the rest waiting; a departing toast gives up its place at once, so a burst does not stutter. The hover-pause **resumes** rather than restarting, which needs the frame clock — `Host.after` gives a timer and no way to ask how much of it has run. The corner decides where the stack sits, which edge a toast slides in from and which end of the column is newest, the last of those as a CSS rule. **The sibling reflow is built** ([ADR-0178](../book/src/adr/0178-a-stack-closes-its-own-hole.md)) — §3's one sanctioned movement effect, and its only implementation. Which toasts move is a fact about the overlay layer rather than about the widget: the column is pinned to a corner with its newest member against it, so a hole in the middle is closed from the far side by the **older** toasts, and a stack that loses its oldest first moves nothing at all. The distance is the departing toast's height, banked from `Measured` because it is gone by the time it is wanted, plus the gap the stylesheet is keeping. **Not built: the live region**, which is M5's like every other widget's semantics.
- **`tooltip`** — attached by attribute (`tooltip="…"`) to any widget; shows on hover *and on keyboard focus* after delay; never focusable itself; plain text v1. **Built** ([ADR-0105](../book/src/adr/0105-a-tooltip-is-an-attribute-not-a-widget.md)): the text rides on `Attributes` — which is what "any widget" means, including one in an application's own module — the event loop gained a timer for the 500ms delay, the router says when the hovered or focused node moved, and the launcher opens a tooltip-kind popup above the node's painted rectangle. It is never light-dismissed: a press would close it in the same gesture as the click on the thing it describes. The target is found by walking *up* from the hovered element, so a tooltip on a `button` survives the pointer being over the button's label.
- **`popover`** — anchored floating panel (the `select` popup generalized): placement with flip/shift when near edges, light-dismiss on outside click/Esc; the primitive under menus, dropdowns, `date-picker`, `color-picker` and autocomplete. **Built, as two halves that are deliberately not one widget** ([ADR-0104](../book/src/adr/0104-a-popup-is-measured-then-placed.md)): `popover` is the *panel* — surface, edge, radius, padding, and a menu shape whose items fill the width — and `host.popup(content, anchor, placement)` is the *opening*, which measures the content, flips and shifts it against the display's work area, opens the platform window and light-dismisses it. The second half serves `tooltip`, `select` and `menu` equally, none of which is a popover, so it does not live inside one. A popup taller than the work area is clamped rather than scrolled **unless its caller says otherwise**: the facility reports what it measured, between the measure and the place, and `menu` and `select` both answer by becoming a panel of the screen's height with their content scrolling inside it ([ADR-0179](../book/src/adr/0179-a-popup-says-what-it-measured.md)). Whether long content should scroll or be clamped is a fact about the content — a tooltip that scrolled would be absurd — so the facility asks rather than deciding.
- **`message`** — an inline banner stating something about the region it sits in: `kind="info|success|warning|danger"`, an icon, text, optional action links, optional dismiss. **Not a `toast`**, and the distinction is the reason both exist: a toast is transient, floats over the window and is about something that just happened; a message is part of the layout, persists until the condition does, and is about the thing next to it. A form's error summary is a `message`; "Saved" is a `toast`. The icon is not decorative — §1.2 forbids colour as the only carrier of meaning, so `kind` sets an icon *and* a colour. Semantics: status for info/success, alert for warning/danger, which is what decides whether it interrupts. **Built** ([ADR-0175](../book/src/adr/0175-a-banner-says-its-kind-twice.md)), with the icon requirement taken literally: the four glyphs are four `Box.Mark` kinds drawn to Lucide's `info`, `circle-check`, `circle-alert` and `triangle-alert`, because a banner is described afresh every build and an `Icon` is native memory somebody has to close. Drawing them found that §1.2's rule had nothing behind it — the hue a glyph is drawn in was below the 3:1 floor in five of eight theme/surface pairs — so a hue has a third rank now (`--gb-danger-line`) and CI sweeps it. Two departures worth stating. **The action links are the author's own widgets** rather than a node this widget invents, because `button class="ghost"` already is one. The **dismiss fades before it tells you** — the × starts the exit in the widget while the banner is still described and calls the handler when it is over, which is what lets a widget with no owner animate its own departure. And **there is no `bind=`**: a banner's *presence* is the thing that changes, and a bound one would be present and empty when there was nothing to say — §8's subset has no `display`, so nothing can take itself out of a layout, and the thing that can is whatever described it. §4's error summary is therefore `Message.summary(controller.errors())`, which is empty when nothing is wrong.
- **`tour`** — a guided sequence of `popover`s over real widgets: each stop names a target by id, a title, a body, and Back/Next/Skip. The window dims outside the target with a `veil` cut to its rect, so the thing being described is the only lit thing on screen. It **scrolls the target into view and waits for the frame** before positioning, because a popover anchored to a rect that is about to move points at nothing. `Esc` skips the whole tour, not one stop. A target that is not in the tree is skipped with a warning rather than throwing — a tour is documentation, and documentation going stale must not take the window down. Semantics: dialog per stop, with the target as its described object.

## 8. `widget.menu`

- **`menubar`** — in-window horizontal bar (a global macOS menubar is a documented non-goal for v1, see ARCHITECTURE §17); `Alt`-style keyboard activation; arrows navigate. **Built** ([ADR-0163](../book/src/adr/0163-a-menu-bar-owns-its-menus.md)): a bar's children are `item`s, and an `item` containing `item`s is a heading that opens a menu — the nesting that has been the submenu syntax since ADR-0106, so there is no new markup. The bar is a horizontal focus scope and one tab stop: `Left`/`Right` walk the headings, `Down`/`Enter`/`Space` open one. Clicking opens; once a menu is down, hovering another heading swaps to it, and hovering with nothing down does nothing. Keyboard activation is **`F10`** rather than a bare `Alt`, which is a modifier released with nothing after it and is not something a `Shortcut` can name. *Not built: `Left`/`Right` between menus while one is showing — the open menu is a separate window with its own focus, which is the same missing item-to-popup callback that keeps `Left` from closing a submenu (ADR-0112).*
- **`menu` / `item` / `separator`** — items: label, optional icon, accelerator (displayed right-aligned *and* auto-registered in the window's shortcut map), checkable items, disabled state, nested submenus (hover-intent timing). Rendered in backend popup windows so menus escape window bounds. **Built, accelerators included** ([ADR-0106](../book/src/adr/0106-a-menu-is-a-widget-and-opening-one-is-not.md), [ADR-0163](../book/src/adr/0163-a-menu-bar-owns-its-menus.md)): the three are widgets and `Menus.open(host, anchor, menu)` is the call that opens one, because opening needs a `Host` and a widget must not have one. A nested `item` *is* the submenu syntax; submenus open beside their row after 150ms of hover intent and close their siblings as they go; choosing any command closes the whole stack. A `menu` is a vertical focus scope, so `Left`/`Right` stay free for "close this submenu" and "open that one". The accelerator is **displayed and registered**, and what made that possible was noticing that only the *popup* is short-lived: a `Menu` is a value, so a `menubar` holding one holds the description for as long as it is mounted, and `Accelerators` walks it. A row is skipped when it has no accelerator, no command, or is disabled; an accelerator that does not parse is logged rather than thrown, because it is a typo already drawn where somebody can see it. A menu that is *only* ever opened — a context menu, a `Menus.open` call — still registers nothing, because nothing is holding it.
- **Context menus** — any widget takes `context-menu="menuId"`; opened by right-click or the keyboard menu key at the focused widget. **Built for the right-click** ([ADR-0108](../book/src/adr/0108-a-context-menu-is-a-name-on-a-widget.md)): the name rides on `Attributes` exactly as a tooltip's text does, the toolkit walks up from what is under the pointer to find it, and `Menus.contextMenus(host, map)` is the one line that says what the names mean — the two halves sit on opposite sides of the module boundary, because only `:core` can notice the click and only the catalog can build a menu. The menu is anchored to the **pointer** rather than to the widget, so two right-clicks in one list open two menus in two places; the press is taken, so right-clicking a button opens its menu rather than pressing it; and an unregistered name is logged rather than thrown, because a right-click is discovered at right-click time and taking the window down is worse than a missing menu. **And for the keyboard** ([ADR-0208](../book/src/adr/0208-a-context-menu-answers-the-keyboard.md)): `Key.MENU` — SDL's `SDLK_APPLICATION`, the key between `AltGr` and `Ctrl` — and `Shift+F10` beside it, because a Mac keyboard has no menu key and a PC one still has users who reach for the pair. Bare `F10` is deliberately not taken: it is the `menubar`'s (ADR-0163). Two things differ from the pointer's half and both follow from there being no pointer — it starts at the **focused** element rather than the hovered one, and it is anchored to that element's **painted rectangle** rather than to a point, so the menu hangs off the bottom of whatever has the focus ring. The walk up to the nearest widget that named a menu is the same code either way, because it is the same rule. Nothing focused opens nothing.
- Semantics: menubar/menu/menuitem with checked state.

## 9. `widget.shell`

- **`tray-icon`** — via SDL3's tray API: icon (theme-aware light/dark variants), tooltip, menu, activate event. Availability is platform-dependent; the API reports absence rather than failing.
- **`titlebar`** — opt-in client-side decorations: drag region, double-click maximize, window buttons with per-platform ordering, frost material variant; falls back to native decorations by default (ARCHITECTURE §4).
- Window chrome helpers: decoration mode switch, fullscreen toggle, attention request (taskbar flash / dock bounce via SDL where supported).

## 10. `widget.collection`

- **`list`** (v1) — vertical list over an observable item model with an item-factory (any widget as row); selection models: none / single / multi (Ctrl/Shift semantics); full keyboard (arrows, Home/End, type-to-select when items expose text); item context menus. **v1 renders instantiated rows** — fine into the low thousands; **virtualization/recycling is the committed v1.x follow-up** (the item-factory API is designed for recycling from day one so it's a performance upgrade, not an API break). Semantics: listbox/option. **Built** ([ADR-0212](../book/src/adr/0212-a-list-owns-the-models-a-tree-borrowed.md)): an item is the *application's* type and three functions describe it — `identity` says what it is, `factory` says what it looks like, and `text` says what it reads as, which is what makes type-to-select conditional the way this row asks. A list with no `text` gets no typeahead and, more to the point, does not **consume** the keystroke. The **selection models moved here from `tree`**, which defined them first under ADR-0184's rule and wrote down that `list` would have to agree; nothing about their shape changed on the way, which is the evidence the promise was small. **Item context menus are named on the row** rather than on what the factory returned, because a right-click walks up from the pointer and the menu key walks up from the **focus** (ADR-0208), and only the row is on both paths. `Home`/`End` go to the ends of the **model** rather than of the viewport, and a row's focus name is scoped by the list's `id` so two lists over the same items do not answer to each other's keys. The class is `ListView` and the CSS type is `list`, because a widget record named `List` would shadow `java.util.List` in every file that built one. **And the virtualization this row commits to is built** ([ADR-0213](../book/src/adr/0213-a-virtual-list-is-two-spacers-and-a-window.md)): `virtualized(rowHeight)` builds only the rows the viewport can see and stands the rest off with two spacers, so ten thousand rows cost about twenty. It is opt-in and takes a **height** rather than a flag, because that is the one number the widget cannot find out — a stylesheet resolves `--gb-list-row-height` and no widget can read a resolved custom property — and because `index × height` is only a position if every row is that height. The spacers are what make it terminate: they absorb every row the window leaves out, so the total height is a function of the model and the node that was measured never moves. `Home`, `End` and the typeahead still reach rows that are not built, by widening the window and then focusing, with a retry because the frame loop fires its timers after the pump. *Not built: rows of varying height, which this arithmetic rules out.*
- **`tree`** — a hierarchical list: an observable node model with a children supplier (lazy, so a node's children are fetched when it first expands), indentation per level, a chevron on nodes that have or may have children, and `list`'s selection models. Keyboard is the part that has to be right: `Right` expands or moves to the first child, `Left` collapses or moves to the parent, `Home`/`End` go to the first and last **visible** rows, `*` expands every sibling, and type-to-select matches across visible rows only. `checkable="none|leaf|any|cascade"` adds a checkbox per node; `cascade` propagates down and shows `indeterminate` upward, which is the one place the tri-state checkbox is not a decoration. Expansion state is retained across rebuilds by node id, not by index — a tree that collapsed itself when its model reordered would be the same defect list keys exist to prevent. It shares `list`'s item-factory so it inherits the virtualization work when that lands. Semantics: tree/treeitem with level, position and expanded state. **Built in a first cut** ([ADR-0184](../book/src/adr/0184-a-tree-is-a-list-that-remembers-what-is-open.md)): the node model with its lazy children supplier, expansion retained by id, the indent-and-chevron gutter, and `Right`/`Left` — which needed the rows flattened depth-first, so that `Right` on an already-open row does *nothing* and falls through to the vertical scope, whose next row is the first child. **And the rest of §3's keyboard is built** ([ADR-0209](../book/src/adr/0209-a-tree-finishes-its-keyboard.md)): `Home`/`End` go to the first and last rows of the **flattened list** rather than of the viewport, which is what every tree means and what `Ctrl+End` means in every document; `*` opens every **sibling** and not every descendant, because a key that opened everything underneath would hang a lazy tree by fetching its whole model on one keystroke; and type-to-select matches **visible rows only**, which is §3's own wording and the rule that keeps it from being a search. All three need rows the focused one cannot see, so all three are callbacks the tree hands down in the shape `Left`'s move-to-parent already had. `*` and the typeahead both arrive as text rather than as keys — `*` is a character whose key differs by layout, and a typeahead wants what was *typed* — and typing moves the **focus** without choosing, which is `select`'s split and ADR-0063's rule. **And the last two are built** ([ADR-0210](../book/src/adr/0210-a-tree-checks-and-selects-two-different-things.md)): `checkable=` puts a box on the rows, and `selection=` is §3's none/single/multi with the Ctrl/Shift semantics. **Selecting and checking are two values reported through two callbacks** — the selection is where the reader *is* and the checks are what they have *marked*, and a file manager where those were one thing could not copy six files. A `cascade` parent's state is **derived** from what is under it rather than stored, so it cannot drift out of step with its own children; a lazy branch nobody has opened reads its own membership, because fetching a model to draw a checkbox is the one thing a lazy tree must not do; and clicking a mixed branch asks for *all* of it, which is `Checkbox.Value.toggled()`'s rule getting its second caller rather than a second copy. The box borrows `check-indicator`, so there is one tri-state mark in the toolkit and not two kept alike by hand. `Space` ticks and `Enter` chooses, and ticking **consumes** the click so it does not also select. Selection reports the **whole set** even when it holds one, because a `Shift` range runs over rows only the tree can see; the three-argument constructor unwraps it again, so `select tree=` sees the id it always saw. `Selection` and `Checkable` are defined here, which is the same debt the node model took on: `list` will have to agree with them. **`tree` now owes nothing further from §3.** §2's chevron `rotate` is two marks instead, for the reason `select`'s chevron already had — §8's subset has no `transform` on a mark. The model was defined here rather than inherited, because `list` is not built, so `list` will have to agree with it.
- **`calendar`** — a month grid over a date model: single date, multiple dates, or a range; `min`/`max` and a `disabled` predicate; per-day decoration from the application (a dot, a `badge`, a background) so an agenda or a heat map is the same widget with a different cell renderer. Week starts and month/day names come from the `Locale` the application supplies — the toolkit ships no calendar data of its own beyond `java.time`. Keyboard: arrows move a day, `PgUp`/`PgDn` a month, `Shift+PgUp`/`PgDn` a year, `Home`/`End` the week. The grid is one Tab stop with a roving day (§2.2). Semantics: grid with each cell's full date as its name, because "14" is not a date. **Built** ([ADR-0274](../book/src/adr/0274-a-calendar-is-told-what-day-it-is.md)), and all of that is here except the second half of the semantics line. `DateSelection` is **one value for three models** rather than `list`'s enum-and-a-set, because a calendar's third model is not a count: a range of two dates is not two dates, since everything between them is shaded and neither end means anything without the other. That is also what makes §2's "radius `full` on the selected day, **range ends only**" one CSS rule — a range's ends are `:checked` and its middle is not — and why §2's **grid gap of 0** is load-bearing rather than a taste: a gap would break a range's shading into seven stripes a week. The grid is **always six weeks**, so a four-week month and a six-week one are the same height and nothing under a popover moves when it pages; the spare cells come from the months either side, drawn quieter and still pressable. §3.1's month cross-fade is **two months at once**, the incoming one in flow and the outgoing one absolutely positioned over it — a single grid dipping to transparent is a dissolve to the background, which on a popover reads as a blink. "One Tab stop with a roving day" is built as one focusable node and a class, because a `FocusScope` roves between *focusable* children and forty-two of those would be forty-two Tab stops. One addition: a **month header** with a label and two arrows, which §10 does not ask for and a mouse cannot do without — `design-system.md` §2 gained its row in the same change. *Not built: each cell's full date as its name, which needs a channel `Semantics` has for no widget (M5).*
- **`timeline`** — an ordered list of events along an axis: each entry has a marker (dot, icon or `badge`), a label, an optional timestamp and optional body content. `direction="vertical|horizontal"`, `align="start|alternate"`. `pending=#true` renders a trailing unfilled marker for "and then what happens next", which is what distinguishes a timeline from a list with dots. Semantics: an ordered list — the connecting line is a drawing and is not announced.
- **`table`** — a `list` with columns: an item model, a **column model** (a key, a header, a width and a cell-factory each), and one row per item. It takes `list`'s selection models, `list`'s keyboard and `list`'s virtualization unchanged, because a table's rows *are* a list's rows with more than one thing in them. **Sorting is the application's**: clicking a sortable header reports the column and the direction it would go to next, and the table draws the caret for whatever sort it is handed back — the same split `select`'s autocomplete draws, and for the same reason, since a table over a database sorts in the query. Columns are sized by their `width`: a fixed number of logical pixels, or a **weight** that shares out what is left, which is flexbox's own arrangement rather than a second one. A cell-factory is `list`'s item-factory per column, so any widget is a cell. The header is one row and is **not** a Tab stop when nothing in it is sortable. Semantics: grid/row/columnheader/gridcell. **Built** ([ADR-0214](../book/src/adr/0214-a-table-is-a-list-with-columns.md)): it is a `list` composed rather than reimplemented — the same `ListView` builds the rows, so the selection, the typeahead, `Home`/`End` and the ten-thousand-row window are inherited rather than written twice, and a bug fixed in one is fixed in both. A row's cells come from the same column model the header does, which is what keeps them in step: there is no way to draw four headers over five cells, because both are `columns().size()` long. *Not built: column resizing by dragging a header edge, which §3's metrics row allows for and nothing has asked for; and horizontal virtualization, which is a different arithmetic and is only worth it past about fifty columns.*

## Cross-cutting notes

- **Retained widget state** (scroll position, selected tab, caret, splitter position, list selection) survives widget-tree rebuilds via element-tree keys — declarative rebuilds never visibly reset UI.
- **Gallery app** exercises every widget in every state in both themes; golden-image CI runs the gallery matrix. A widget isn't "done" until it's in the gallery. **Built** ([ADR-0110](../book/src/adr/0110-the-showcase-is-a-gallery-of-screens.md), restructured by [ADR-0222](../book/src/adr/0222-a-showcase-is-a-window-a-bar-and-seven-screens.md)): the showcase is a `menubar`, a bar and **seven** screens behind one tab strip — Basic, Panels, Overlays, Forms, Navigation, Collections, Charts — each of them a wall of cards in a `masonry`, and each card a `card` or a `group-box`. Four screens are `.kdl` documents with Java appending only the cards markup cannot write, the split being about what markup cannot *say* rather than about appearance. Eleven golden images cover them, and a widget has a screen to be on: `select` and every §3 control belong on Basic, §4's fields and §3's three choosers on Forms, `dialog`/`toast`/`message` on Overlays, `list`/`table`/`tree` on Collections.
- **KDL/Java/CSS parity test** walks the registry: every widget constructible from markup, from the builder, and matched by its type selector — build fails otherwise.
