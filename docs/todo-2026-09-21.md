# Six red jobs, five causes

Working notes for 2026-09-21, the day after
[`todo-2026-09-20.md`](todo-2026-09-20.md). Status legend as in
[`todo-sweep.md`](todo-sweep.md): **done** — code, tests and ADR landed;
**in progress** — being built now; **open** — not started; **answered** —
decided not to build, with the reason recorded; **blocked** — the thing it waits
on is not in this repository.

## 1. What is red

Both on `9a768bd3`. Snapshot run 25 and Showcase run 21, six failing jobs
between them and **three** causes — the count matters, because the two runs
look like one problem and are not.

| Run / job | Step | Cause |
|---|---|---|
| Snapshot · `windows / libgoldberry (windows-x64)` | Build | **A** — `C1083: Cannot open include file: 'WebView2.h'` |
| Snapshot · `windows / Verify layouts (windows-x64)` | `download-artifact` | **A**, downstream — the artifact was never uploaded |
| Showcase · `windows-x64` | Build libgoldberry | **A** again, through Ninja rather than the VS generator |
| Showcase · `linux-x64` | Run the native image | **B** — `MissingForeignRegistrationError` |
| Showcase · `macos-aarch64` | Run the native image | **C** — 197 of 300 frames late, budget 30 (a check that had never run there) |

Everything else was green: both Linux legs, both macOS legs and all three `Java`
jobs of the snapshot. The `Verify layouts` failure is [ADR-0016] working exactly
as designed — that job runs `if: !cancelled()` so that a missing artifact fails
loudly rather than skipping quietly. It did.

## 2. Cause A — the WebView2 headers

`natives/src/main/cmake/CMakeLists.txt` said, in the section that decides
whether to build `libgoldberry-webview`:

> WKWebView is a system framework and WebView2 ships with the OS, so there is no
> optional header to probe for.

The WebView2 **runtime** ships with the OS — it is Edge. The **SDK header**
`WebView2.h` does not; it is in the `Microsoft.Web.WebView2` NuGet package, and
`webview.h` includes it by name. webview's own CMake downloads that package, and
this build deliberately does not use webview's CMake, so nothing downloaded it.

This is a missing dependency, not a regression in anything written that day: the
Windows leg would have failed the first time it compiled the shim, which is the
commit that added it.

### Done

**Fetch the SDK headers, pin them in the catalog, probe for the result** —
[ADR-0450]. `webview2 = "1.0.1150.38"` in `gradle/libs.versions.toml`, fetched
on Windows only, headers only, and not fatal when absent — the same shape Linux
has had since ADR-0441.

Verified here, on Linux, as far as Linux can verify it:

- the whole superbuild reconfigures and builds, so the new `goldberry_pin` reads
  the new catalog key: `Goldberry pins: … webview 0.12.0, webview2 1.0.1150.38`;
- the `web view: ON (webkit2gtk-4.1)` line still prints, through the rewritten
  message that now names the engine rather than the pkg-config module;
- the `FetchContent_Declare` block was run standalone against nuget.org: it
  downloads, extracts, and `find_path` lands on
  `…/mswebview2-src/build/native/include`. This was the part worth checking —
  the URL's last component is a bare version with no extension, which is why
  `DOWNLOAD_NAME` is set.

**Four new guards in `SuperbuildTest`**, which is where the build files are read
as text:

| Test | Guards |
|---|---|
| `everyUpstreamIsPinnedFromTheCatalog` | every `${GOLDBERRY_*_REF}` an upstream interpolates is set by a `goldberry_pin()`, and that key exists in `libs.versions.toml` (ADR-0035) |
| `archiveUpstreamsNameTheirDownload` | a URL-fetched upstream sets `DOWNLOAD_NAME`, or CMake silently does not extract it |
| `theWindowsWebViewSdkIsFetched` | the SDK is fetched and probed for, and reaches the shim as an include directory with no `WebView2Loader` on the link line |
| `theWebViewOffMessageIsPlatformSpecific` | the "web view: OFF" line carries a per-platform reason, rather than telling a Windows reader to install a Debian package |

The first is the general one: it would have caught a version hardcoded into the
CMake, which is the mistake ADR-0035 exists to prevent and which nothing checked
before.

## 3. Cause B — a foreign shape nothing recorded

The Linux image built, started, painted and died on its first frame, asking the
desktop whether to move less:

```
MissingForeignRegistrationError: Cannot perform downcall with leaf type (long,int,long)long
  at ...desktop.calls.PortalSettings$Call2.<init>(PortalSettings.java:252)
  at ...Window.reducedMotion(Window.java:257)
```

**Not from the web view work.** It came in with `bb470b5f`, "The desktop is
asked whether to move less" — the first commit to bind a library that is not
`libgoldberry`. Those bindings go through `Bindings` rather than `Downcalls`
([ADR-0383]) and so were never recorded for the image's metadata; worse, the
descriptor was *built* inside the constructor that links it, which runs only on
a machine that has libdbus. This machine does not, so the metadata generated
here was silently short of five shapes.

That is why nothing caught it: the JVM needs no metadata, the image *builds*,
and the failure needs a machine that has libdbus running an image built by one
that might not. The showcase is the only job that runs an image at all.

### Done

**Declare the shape where it can be reached, link it where the library is** —
[ADR-0451]. `Downcalls.describe` is the twin of the existing `Upcalls.describe`;
the nine descriptors in `…desktop.calls` are constants declared through it, and
the link stays exactly where it was and stays conditional.

Two tests, both of which **fail on the old code and pass on the new**, verified
by stashing the fix and re-running:

| Test | Guards |
|---|---|
| `systemLibraryShapesAreDeclared` | the five system-library shapes are reported whatever this machine has installed — which is the property that matters and the one having the library cannot check |
| `systemLibraryShapesAreConstants` | no descriptor is written inline at a `Bindings.link(…)` call site, so the next holder cannot reintroduce it |

Four of the five failed before the fix. The fifth, `void(void*, void*)`, passed
by coincidence: a `libgoldberry` holder happens to have the same shape. The
generated metadata goes from 77 downcall shapes to 82, measured by generating
the file with and without the fix on this machine.

macOS and Windows had the identical hole in `MacMotion` and `WindowsMotion` and
are fixed by the same change, though neither had reached it yet.

## 4. Cause C — the macOS frame budget

The macOS image built, ran, and painted all three hundred frames. Then:

```
FrameBudgetException: over the late-frame budget of 30: 300 frame(s) painted,
197 late; paint mean 7.05 ms, worst 331.22 ms; display 60.0 Hz
```

This read as a performance regression and is not one. Run 20 — the last green
showcase, at `64596a97` — had expired logs, so it was **re-run** rather than
guessed at (`rerun_workflow_run` re-runs at the original commit, which is
cheaper and cleaner than pushing a branch at an old SHA). What the macOS leg
used to do:

```
./goldberry-showcase-macos-aarch64 --frames=3
```

Three frames, no resize walk, no budget. The 300-frame budgeted run came in
*with* ADR-0342, after that green run. So run 21 was the first time macOS was
ever asked, and it has never passed — and neither has anyone else: Windows has
never got past building libgoldberry, Linux has never got past its own missing
foreign registration. **No leg on any platform has ever completed the run.**

Which makes the interesting defect the one in the comment above the budget:

> The budget is a tenth of the frames, and it is a ceiling on a GPU-less
> virtual machine painting into a software X server, Cocoa or D3D — evidence
> about three platforms' drivers, not a claim about hardware.

There was no evidence about any of the three. The number was reasoned about and
then made a verdict.

### Done

**The budget is asserted where the display is pinned** — [ADR-0452]. The
justification was already in the workflow, three lines under the budget:
`xvfb-run --server-args="-screen 0 1920x1200x24"`. A refresh budget is a number
about a particular screen, so it compares across runs only where the screen is
the same across runs, and Linux's is the only one this workflow chooses. The
macOS window maximized to 1920×942 because that is the VM's screen; nothing
here asked for it.

macOS and Windows run the identical walk and report their summary into the step
summary; they no longer turn it into a verdict. The `painted 300 frame(s)` grep
still fails them, so a hang or a crash is still a red job.

**No number was invented**, which was the alternative and would have repeated
the mistake with one data point instead of none: a budget has to sit above what
the machine does and below what a regression does, and 197 locates neither
edge. Once Linux has run green a few times there will be a measured
distribution to set ceilings from — for all three. The note in `showcase.yml`
says so.

## 5. The second round — what the first round uncovered

Snapshot run 26 on `172956e3` is **green**: causes A and B confirmed fixed in
CI, Windows building and Verify layouts passing. Showcase run 22 on the same
commit has macOS **green** — three hundred frames painted, 200 late, reported
and not judged, which is ADR-0452 working. It also turned two more jobs red,
and both had been broken all along behind the failures that used to come
first.

### Cause D — the Windows link line

```
[679/681] Linking CXX shared library goldberry.dll
FAILED: The command line is too long.
```

8541 characters, of which 7697 are 253 `/INCLUDE:` flags. `CreateProcess`
would take 32767; Ninja runs the link through `cmd.exe /C`, which stops at
**8191**. `windows.yml` was green on the same commit because the Visual Studio
generator routes the link through MSBuild's own response file — one commit,
two Windows jobs, opposite results.

**Done, at the second attempt** — [ADR-0454].

The first attempt was a response file, `goldberry.force`, handed to link.exe as
`@file`. It fixed Ninja and broke the Visual Studio generator:

```
LINK : fatal error LNK1104: cannot open file '@...\goldberry.force'
```

**Response files do not nest.** MSBuild already passes the whole link through
one of its own, so the `@file` inside it is never expanded and link.exe reads
it as the name of a file to link. Snapshot run 27 is that failure; run 26,
before the change, was green.

That is the same two-generator disagreement as the original bug in the other
direction, and it is the lesson: any fix that is a link *argument* is one the
two generators handle differently. So the directives go off the command line
altogether, as `#pragma comment(linker, "/INCLUDE:...")` in a generated source
compiled into the library — the compiler writes them into the object's
`.drectve` section and the linker reads them from there whatever spawned it.

Checked by generating it: the CMake block run standalone against
`exports/goldberry.symbols` produces 253 pragmas for 253 symbols and compiles
as C. That MSVC *honours* them needs a Windows runner and is the one thing
still unverified. `msvcForceLinkListIsInTheObject` now refuses both wrong
answers — the inline flags and the response file — because the second is the
mistake a reader of the first half of ADR-0454 would make again.

Worth noting it was nobody's regression: `eb30c1bf` renamed 25 symbols to
`goldberry_hb_*`, ten characters longer each, and ADR-0385 added six. The list
had been creeping toward the limit for months with nothing watching.

### Cause E — resources declared by the wrong module

The Linux image painted, then died on the first paragraph with an emoji:

```
/io/github/digitalsmile/goldberry/emoji/fonts/OpenMoji-color.ttf is missing
from goldberry-emoji, which means this jar was assembled without the asset step
```

The message is wrong — the jar has the font. What was missing is the
declaration that puts a resource *inside a native image*. `:core`, `:widgets`
and `:example` each ship a `reachability-metadata.json`; `:emoji` shipped none.

`:core`'s own metadata predicted it, in the comment on why globs beat traces:
"Inter but neither JetBrains Mono nor **OpenMoji** — because the run never
switched theme and never drew mono text or an emoji". True when written, and
then ADR-0384 moved the face to `:emoji` and ADR-0387 moved it under that
module's package, and the declaration followed neither.

**Done** — [ADR-0453]. `:emoji` declares its own font.

**And `:html` had the same hole**, found while checking the others. It ships two
stylesheets, reads both by name, declared neither — and works today only
because the showcase *traces* a run that opens the Markdown and HTML screens,
so `:example`'s traced metadata lists them literally. Luck, and not luck that
travels: anyone else taking `:html` and tracing a run without a document gets
an image whose stylesheet is not in it. `:html` now declares its own.

**The guard is repository-wide**, because per-module is what was forgotten
twice. `DeclaredResourcesTest` in `build-logic` holds every module's shipped
resources to that module's **own** globs — and the "own" was learned here: the
first version pooled all modules' declarations, saw `:example`'s traced list
covering `:html`, and passed. Verified failing for `:html` once its file is
removed; `DeclaredFontResourceTest` covers `:emoji`, whose font is generated by
the asset step rather than committed and so is invisible to a source walk.

## 6. Open


**The second library is built and then discarded, on every platform.** Each
`upload-artifact` names exactly one file — `libgoldberry.so`,
`libgoldberry.dylib`, `goldberry.dll` — so `libgoldberry-webview` has never been
in a published jar, on any platform, since ADR-0441. Nothing is broken by this
today: `WebviewLibrary` looks for a sibling of the library it loaded, finds
none, and `Capability.WEB_VIEW` is absent, which is the documented degraded
state. But it means the feature is unreachable for everyone who consumes the
published artifacts rather than building from source, and the "*unverified on
Windows and macOS*" caveat is doing double duty for "and unshipped everywhere".

Packaging it is a real decision rather than an oversight to correct in passing:
the classifier jar layout, the sibling-lookup contract and the Linux artifact's
`libwebkit2gtk-4.1.so.0` pin are all involved, and the manylinux container may
not even be able to produce one (see the long comment on the optional
`dnf install` step in `linux.yml`). Left open, deliberately.

**Windows and macOS remain run-time unverified**, as ADR-0441 says. What changed
today is that Windows now *compiles and links* the shim, which is strictly more
than it did; nobody has opened a page on either platform.
