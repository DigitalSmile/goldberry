## Causes

1. **The Diagnostics golden photographed the build machine.** The capabilities
   card read `Goldberry.capabilities()`, and the golden was taken here, where the
   library is built without ibus and udev. CI's says yes to both. The diff was
   three badges, the same 1566 pixels on all three platforms. ADR-0554.
2. **`@TempDir` is not the project directory Gradle holds.** `ProjectBuilder`
   canonicalises it. On macOS `/var/folders/...` becomes `/private/var/...`. On
   Windows `C:\Users\RUNNER~1\...` becomes `C:\Users\runneradmin\...`. The two
   tests built their expected paths from the `@TempDir`. They now build them from
   `project.getProjectDir()`. `AssetToolTest.catalogs` also compared a Windows path
   with `String.endsWith("a/b")`, and now compares `Path`s. Reproduced on Linux by
   running the test JVM with `java.io.tmpdir` on a symlink: 2 of 8 failed before
   the change and none after.
3. **`SourceDocsTest` had never read build-logic's own sources on Linux or
   macOS.** It dropped build output with `file.toString().contains("/build/")`,
   which also matches the package directory `dev/goldberry/build/`. On Windows the
   separators are backslashes, so nothing was dropped and the rule saw six lines
   for the first time. The filter now matches `build/` and `.gradle/` at the root
   or in a module, on the path from the root, and Linux reports the same six lines
   as Windows. They are in `CodeQlSuiteTest` and `BenchmarkLaneTest`, whose
   subject is the testing notes. They are allowed by name, the way
   `DecisionLogTest` may cite records.
4. **`TooltipTest.aLengthIsNotADelay` read a clock it did not check.** It hovers,
   waits 250 ms and asserts no tooltip against the 500 ms default. A runner that
   reads it after 500 ms sees the tooltip, rightly. The test now records when it
   hovered and when it looked. A look after the default came due is inconclusive
   (an assumption aborts the run) rather than a failure. A real `60ms` token still
   fails it: checked by hand. The second Windows run on the branch then failed
   `waitsForTheDelay` ("60ms is not 500ms") the same way, so all three tests that
   assert a tooltip is *not up yet* share `assumeReadBeforeTheDelay`. A 10 ms
   delay still fails `waitsForTheDelay`. The third run failed
   `aClickDoesNotPinTheTooltip`: the delay fired late, the tooltip opened just
   before the 900 ms read, and the exit posted 150 ms later fell inside
   `HostedWindow`'s 250 ms spurious-exit window, where swallowing it is correct.
   The exit now comes 400 ms after the tooltip was *seen*, which is no earlier than
   it opened. The tests that need a tooltip up poll for one (`whenTheTooltipIsUp`)
   instead of reading at 900 ms. Reverting the focus-fallback fix still fails the
   test. Last, `theDelayIsAToken` failed here under a saturated full check: a
   loop that took the hover late started the 60 ms late too, and the read at
   250 ms from the *post* came before it. It now reads 250 ms after the window
   took the hover, which is when the target's `cursor: pointer` reaches it. With
   no token it still fails.
5. **Qodana inspected the benchmarks as production code.** ADR-0551 gave them a
   source set of their own, which IntelliJ imports as production. 51 of the 54
   high findings were in `src/benchmark`. ADR-0555 excludes `src/benchmark` and
   `src/jmh`. Two real findings in `:example` are fixed: `SecondWindowCard` drops
   its close listener with the card, and `BoundTextCard` no longer passes a
   possibly-null value to a field.

## The SDL audio sink on Windows: a starved runner

Three tests failed on the Windows runner against SDL's dummy driver, and passed
on Linux and macOS. They had never run on Windows before ADR-0553:

- `drainsSmoothly`: "only 1 readings before the queue ran dry", with two seconds
  of audio written;
- `rate`: "drained at 1.34x the wall clock, asked for 4x";
- `latency`: "no pull was seen" within 500 ms.

A diagnostic branch, `diag/windows-audio`, ran a probe on `windows-2022`. It
printed the raw `SDL_GetAudioStreamQueued` readings over three seconds at rate 1
and rate 4, and the sleep resolution. In the same run the three tests passed. The
probe showed why they fail when they do: the runner starves threads while
Gradle runs the modules' tests side by side.

| Reading | Linux, here | Windows runner |
|---|---|---|
| `Thread.sleep(1)` min/median/max | 1.07 / 1.08 / 3.33 ms | 1.02 / 3.02 / 87.82 ms |
| `Thread.sleep(10)` max | 10.09 ms | 141.97 ms |
| Device pull gap, median/max (rate 1) | 21.1 / 23.9 ms | 24.4 / 183.1 ms |
| Device pull gap, median/max (rate 4) | 21.1 / 21.6 ms | 54.4 / 318.6 ms |
| Queue readings in 3 s, rate 4 | 5260 | 67 |

So "only 1 readings" was the 300 ms deadline passing after one stalled
`sleep(1)`, and the message blamed the queue. "No pull was seen" was a device
thread or test thread descheduled for half a second. And 1.34x was the starved
device thread really consuming that slowly against the wall clock.

What changed in `SdlAudioSinkTest`:

- **`rate`** plays a stream at 4 beside a stream at 1 on the same dummy device.
  The device's one thread takes a buffer from each stream in the same pass, so
  the fast queue drains four buffers for the plain one's one however the thread
  is scheduled. The ratio must be at least 2. With the fast stream mutated to 1
  the test fails at exactly 1.0x.
- **`drainsSmoothly`** counts readings where the sink's queue moved while SDL's
  own queue did not (`SdlAudioSink.rawQueuedSamples()`, package-private for this),
  and needs three. A stepping queue never has one, whatever the scheduling. It
  used to ask that more than half of all readings moved, which is the scheduler's
  number: on a saturated machine here the device pulled late, the estimate
  rightly stalled a pull ahead of it, and 10 of 39 moved. With `queuedSamples()`
  mutated to return the raw queue it fails at 0 of 39. It also waits up to 1.5 s,
  short of the 2 s queued, for its readings, and says whether it stopped at the
  deadline or at an empty queue.
- **`latency`** waits up to 2 s for the first pull, and takes up to 500 ms as one
  pull, because a late reader sees several land as one.

Each deadline only bounds how long a failure takes. A passing run ends as soon
as it has its readings. Locally, with every core held by a busy loop and Gradle
pinned to two CPUs, the class passed three times out of three.

- `MediaPlayer playing video, against FFmpeg > plays audio and video to the end`
  failed once locally, in a run that rebuilt and retested every module at once
  (`--rerun-tasks`): `[BUFFERING, PLAYING, BUFFERING, ENDED]` where
