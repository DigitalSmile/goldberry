# After the batch: what was left, and what is being taken

Working notes for 2026-09-20, the day after
[`todo-2026-09-19.md`](todo-2026-09-19.md) closed thirty-one entries and
[`review-2026-09-18-fixes.md`](review-2026-09-18-fixes.md) answered the whole
review. Status legend as in [`todo-sweep.md`](todo-sweep.md): **done** — code,
tests and ADR landed; **in progress** — being built now; **open** — not started;
**answered** — decided not to build, with the reason recorded; **blocked** — the
thing it waits on is not in this repository.

The fourth bucket is smaller than it looks. Read one at a time: a field's scroll

broken* and what is missing is a test nothing can provoke; the third text rank

turned out to exist.

## 3. A `tour` finds its own viewport

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| A `tour` cannot find the viewport its target is in | a walk from a named target to its nearest scrolling ancestor | 0439 | **done** |

**The entry was wrong about itself**, which is the fourth time in this run of
work and the most expensive kind: it had been re-read against the code and
marked "it stands", so the cost was two milestones of an API every tour had to
carry. Its two premises are both true —
`BuildContext.findAncestorState` does walk up from the element being *built*, and
a tour does want a walk up from the element it *names* — and the conclusion does
not follow from them, because `Element` **implements** `BuildContext`. The walk
runs from whatever element it is called on. The target element was already in the
tour's hand: `Host.anchor(id)` returns a hit-test region whose `owner()` is that
element, and `TourState` was calling it on every build for the rectangle and
discarding the owner.

ADR-0120 had written the answer down three hundred decisions earlier —
"`findAncestorState` is added and used by nothing in the end … but it stays,
because it is how an application-level `scrollIntoView` from *inside* a scroll
view reaches the viewport" — and nobody read it back.

**What landed**

- `ScrollScope` in `widgets.core.scroll` — `enclosing(element)` and two `reveal`
  overloads. A new type rather than a static on `ScrollController` because the
  two are opposite directions and only one is a handle somebody owns; a
  discovered `ScrollController` would have an `onChange` that never fires.
- `ScrollState.reveal` — the "how far out of view is this" arithmetic, moved off
  `ScrollController` so that both doors share one copy of it.
- `TourState.reveal` — the controller the application named still wins, because
  the walk finds the **innermost** viewport and an application that names one may
  deliberately mean an outer one.
- `Stop`'s fourth component is now the exception rather than the requirement.

**Three things worth knowing afterwards**

- **The reveal path had no test at all.** `TourTest` drives everything against a
  stub host, and a stub cannot move pixels. It now drives a real painted viewport
  whose regions the stub answers with — and the new test was checked failing
  first: row 20 sits at `314.0` without the walk.
- **A `scroll` named by its own id resolves to itself.** Found by a test
  asserting the opposite: an `id` on a `scroll` lands on the `ScrollViewport` the
  widget builds, not on the stateful node, so the first parent of the only
  element anybody can name is the state holding the offset. Harmless — a viewport
  revealed inside itself moves nothing — and now pinned rather than assumed.
- **The scroll tests had a leaked render tree.** Lifting `ScrollControllerTest`'s
  private harness into a shared `ScrollHarness` found it: the one test that
  builds two harnesses in a single method was closing only the second, because
  each constructor overwrote the field the teardown read.

**Not closed by this**: nested viewports are revealed in the innermost one only,
which is exactly what a hand-wired controller did. Written on `ScrollScope` as
the place it stops telling the truth rather than left to be discovered.

## 3a. `goldberry-web` was not a module, and is built

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| `goldberry-web` is parked, not deferred | a web page on screen | 0441 | **done** — as §9's `web-view`, not as a content module |

**The fifth entry in this run that was wrong about itself**, and the pattern is
now worth naming: every word of it was true, and none of it was about the
question. It said libservo is Rust-only against a deliberately unstable API, so
the module would own a `cdylib` shim and its breakage — correct, and it is why
nothing was built. What it never asked is whether a page needed an engine of this
project's at all.

`webview/webview` is MIT, is one 4500-line header with the implementation in it,
and **brings no engine**: it drives the WebKitGTK, WebView2 or WKWebView already
on the machine. So neither condition ADR-0190 quarantines for — a heavy native
payload, an attribution or copyleft obligation — applies. "Parked" had read like
an answer for two milestones.

**What decided the shape was Wayland, and it took two passes to get right.** The
first draft of the ADR was a companion window aligned to a widget's box, written
before the positioning half was checked. It does not survive: a Wayland client is
not told where it is and may not say where it goes, which is already written into
the SPI — `BackendWindow.position()` returns an `Optional` documented as *"empty
when the platform will not say"*. Reparenting is out for an independent reason
(no cross-process surface adoption). So both ways of making a platform window
look like a widget are closed on the default Linux desktop, and a page is a
**window the application opens**, with `tray-icon`'s exact shape.

**What landed**

- `libgoldberry-webview`, a second shared library built only where WebKit's
  headers are present, linked into nothing and opened on demand. `objdump -p
  libgoldberry.so` shows no GTK or WebKit entry — that one command is what the
  whole separation argument reduces to.
- `natives.webview` (the binding, qualified to `:core`), `render.web` (the SPI,
  the spec, the engine seam), `widgets.shell.web` (`WebPage` and `WebViews`).
- `Capability.WEB_VIEW`, which is the **first capability that is not a bit in
  `libgoldberry`** — it is the presence of the second library, so
  `PlatformCapabilities` gained a two-argument `read` and the enum-parity test
  gained a named exception rather than being deleted.

**Three things worth knowing afterwards**

- **The event loop had to learn to stay awake.** Draining GLib once per iteration
  is not enough: the loop parks in `pumpEvents` for its one-second heartbeat on an
  idle desktop, and nothing wakes it when WebKit has work. A page serviced once a
  second does not scroll. So the wait is capped at 8 ms **while a page is open and
  only then** — the honest fix needs a descriptor from
  `g_main_context_get_poll_func` handed to SDL to wait on, and SDL has no API for
  waiting on somebody else's. Found by reading the loop, not by running it.
- **`webview/webview` 0.12.0 has a bug on its GTK backend.** `set_size_impl`
  applies the size through a complete if/else chain and then falls off the end
  into `return error_info{WEBVIEW_ERROR_INVALID_ARGUMENT, "Invalid hint"}`
  unconditionally — the final `else` is missing. Every resize on Linux succeeds
  and reports failure. The shim checks the hint itself and translates that one
  code; a bogus hint still returns −2.
- **Two GTK majors in one process is a SIGSEGV, and the tray puts one there.**
  The worst of the three and the last found, because it needed the showcase's own
  button pressed: `GdkDisplayManager` is registered by both `gdk-3` and `gdk-4`
  into GObject's process-global type registry, so the second one back gets 0,
  `g_once_init_leave_pointer` asserts, and `gtk_init_check` dereferences NULL.
  SDL's Linux tray is libayatana-appindicator, which links `libgtk-3` — so any
  application showing a `tray-icon` is a GTK 3 process before anybody asks for a
  page, and a web view built on `webkitgtk-6.0` makes it a GTK 4 one. The Linux
  build therefore links **`webkit2gtk-4.1`**, against webview's own preference,
  and the shim additionally checks with `RTLD_NOLOAD` whether the rival major is
  already mapped and declines to open a page rather than killing the process.
  Both probes had passed: neither had a tray, so neither had GTK 3.
- **An ABI check that runs after the binding is not a check.** Found by the same
  crash's clean-up: a stale `libgoldberry-webview.so` left in an install
  directory failed with *"does not export goldberry_webview_gtk_conflict"*
  instead of *"this library is ABI 1 and this build binds ABI 2"*, because
  `WebviewCalls.bind` looked up every symbol and `Downcalls.symbol` threw on the
  first missing name long before the version was read. The probe is bound and
  asked **alone**, first. A version check is only worth writing if it is the
  thing that runs when the version is wrong.
- **An optional feature must not be able to break the call that lists features.**
  The same stale library took `Goldberry.capabilities()` down with it —
  `ExceptionInInitializerError` out of a static initialiser, and then, because a
  poisoned class throws a bare `NoClassDefFoundError` on every later touch, the
  `catch` that handled the first one asked again and got an error with none of
  the cause on it. Binding now answers empty for every failure, and
  `PlatformCapabilities` asks once, outside the `try`.
- **The pump must not touch the library.** It is called once per frame in every
  application that has ever run, and the obvious implementation loads
  `libgoldberry-webview` — and with it GTK and WebKit — on the first frame of a
  process that never asked for a page. An open-page counter is read first, and
  there is a test that calls `pump()` a thousand times to pin it.

**Not closed by this**: Windows and macOS are unverified, in the tray's sense.
The design says SDL's own pump services a `WKWebView` and a WebView2 `HWND`
created on the UI thread, and nothing here has run either.

## 4. What is left after this

With §5 decided, **M5 has no toolkit work left in it**. What remains under that
milestone is the release half — a publishing chain that is built and has never
run, and the three-platform frame evidence M1 is waiting on — and both are
blocked on a Maven Central account and a tag rather than on code.

So the workable list is short and honest: **M4 (GPU)**, which is untouched and
has no external blocker, and the handful of §1 entries that are genuinely
unbuilt. Everything else in `TODO.md` is a decision already taken, a thing
blocked outside this repository, or — as of today — on hold.

**§3a is the correction to that paragraph**, made the same day it was written.
"Workable" was read off the entries' own words, and `goldberry-web` said it was
parked on an unstable Rust API — so it was counted as blocked and not as work.
It was neither. The lesson is §1's, turned on this document: an entry that
explains why it cannot be done is the kind most worth re-reading, because nobody
re-reads it.

## 5. The AccessKit bridge is on hold

| Item | Decision | ADR | Status |
|------|----------|-----|--------|
| The AccessKit bridge, and the six entries behind it | not built, no milestone owns it | 0440 | **on hold** |

**Taken today.** Not deferred to a later milestone — that names a date, and
there is none.

The interface was never the difficulty, and the first framing of it here was
wrong: `accesskit_c` is a C API with a cbindgen-generated header covering all
three platform adapters, and it can be had either by driving cargo from CMake
through Corrosion **or** by consuming the project's prebuilt package, which
exists so that toolkit developers need not deal with Rust at all. Both routes
were open.

What decided it is the toolkit's own argument, one level up. Every one of the six
entries refuses to write a constant until something consumes it — *"a role
nothing consumes is a value written for a bridge that does not exist"* — and:

- **nothing has asked.** This joins §12's bucket of work waiting on a consumer
  rather than on a decision;
- **two of its three platforms cannot be run here.** UIA and NSAccessibility sit
  behind the same missing Windows and macOS machines that already block the tray
  on two platforms, the MSVC `.def` and the Mach-O visibility branch. An
  accessibility bridge shipped untested on two thirds of its surface fails
  silently, and fails the people with no other way in;
- **the cost is permanent and lands in `:natives`** — a Rust toolchain on four
  platforms and in CI, or four platforms of vendored prebuilt binaries, which is
  the same licence-and-provenance question PDFium is already parked on.

**Nothing was removed.** `Role`, `Live`, `Semantics` and `SemanticsSweepTest`
stay: the sweep pays for itself today by stopping a focusable widget shipping
with no name, and the data in the tree is what keeps a bridge an adapter rather
than a rearchitecture if it is ever reopened. The six entries keep their prose
and gain an **On hold** paragraph.

**Said plainly where a reader looks**: `README.md` now states that there is no
screen-reader support on any platform and none scheduled, beside the part of
§4's baseline that *is* built and checked — keyboard reachability, focus ring,
WCAG AA contrast, hit targets, reduced motion, 150% text scale.

## 6. What it would have cost the native build, kept for the record

Written before §5 was decided, and kept because a decision to stop is only
readable beside what stopping avoided — and because these are the two rows to
re-read if anybody reopens it.

`docs/ARCHITECTURE.md` §13 named AccessKit and called it "C ABI, fits the FFM
stack". The interface is exactly that — `accesskit_c` is a C API with a
cbindgen-generated header, covering the core data structures and all three
platform adapters, which is one API where the alternative is three.

The build was the part worth deciding, and it is **not** "the superbuild learns
Rust" as first assumed here. There are two ways in, and the project supports both
deliberately:

| | What it costs | What it costs later |
|---|---|---|
| **Build from source** | `accesskit-c` drives cargo from CMake through Corrosion, so `:natives` gains a Rust toolchain on four platforms and in CI. Cross-compiling needs `Rust_CARGO_TARGET` beside the CMake triple | Nothing. One superbuild, one artifact, reproducible from source like every other dependency here |
| **Consume the prebuilt** | Nothing. The project ships a package of header, static and dynamic libraries per platform — in its own words, so that toolkit developers "won't need to deal with Rust at all" — and `find_package(ACCESSKIT)` wires it up | A **vendored prebuilt**, which is the thing `TODO.md` already has open as a licence-and-provenance question for PDFium. Four platforms of somebody else's binaries in the release |

The second row is cheaper today and takes on the debt the first row does not.
It is the same trade PDFium is parked on, so answering it here answers it there.

Everything downstream of that — `Role` gaining `LINK` and the list roles, a trail
becoming a landmark, `Semantics`' value channel and per-cell channel, `isModal`'s
second consumer, a toast being announced — is nine items' worth of work across six
entries, and none of it could start until one of those two rows was picked,
because the shape of the adapter is the shape of what is linked into
`libgoldberry`.

**Neither row was picked. See §5** —
[ADR-0440](../book/src/adr/0440-the-accessibility-bridge-is-on-hold-and-the-semantics-tree-stays.md).
