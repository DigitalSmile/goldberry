## 3. A `tour` finds its own viewport

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| A `tour` cannot find the viewport its target is in | a walk from a named target to its nearest scrolling ancestor | 0439 | **done** |

**The entry was wrong about itself**, which is the fourth time in this run of
work and the most expensive kind: it had been re-read against the code and
marked "it stands", so the cost was two milestones of an API every tour had to
carry. Its two premises are both true —
`BuildContext.findAncestorState` does walk up from the element being *built*, and
a tour does want a walk up from the element it *names* — and the conclusion does
not follow from them, because `Element` **implements** `BuildContext`. The walk
runs from whatever element it is called on. The target element was already in the
tour's hand: `Host.anchor(id)` returns a hit-test region whose `owner()` is that
element, and `TourState` was calling it on every build for the rectangle and
discarding the owner.

ADR-0120 had written the answer down three hundred decisions earlier —
"`findAncestorState` is added and used by nothing in the end … but it stays,
because it is how an application-level `scrollIntoView` from *inside* a scroll
view reaches the viewport" — and nobody read it back.

**What landed**

- `ScrollScope` in `widgets.core.scroll` — `enclosing(element)` and two `reveal`
  overloads. A new type rather than a static on `ScrollController` because the
  two are opposite directions and only one is a handle somebody owns; a
  discovered `ScrollController` would have an `onChange` that never fires.
- `ScrollState.reveal` — the "how far out of view is this" arithmetic, moved off
  `ScrollController` so that both doors share one copy of it.
- `TourState.reveal` — the controller the application named still wins, because
  the walk finds the **innermost** viewport and an application that names one may
  deliberately mean an outer one.
- `Stop`'s fourth component is now the exception rather than the requirement.

**Three things worth knowing afterwards**

- **The reveal path had no test at all.** `TourTest` drives everything against a
  stub host, and a stub cannot move pixels. It now drives a real painted viewport
  whose regions the stub answers with — and the new test was checked failing
  first: row 20 sits at `314.0` without the walk.
- **A `scroll` named by its own id resolves to itself.** Found by a test
  asserting the opposite: an `id` on a `scroll` lands on the `ScrollViewport` the
  widget builds, not on the stateful node, so the first parent of the only
  element anybody can name is the state holding the offset. Harmless — a viewport
  revealed inside itself moves nothing — and now pinned rather than assumed.
- **The scroll tests had a leaked render tree.** Lifting `ScrollControllerTest`'s
  private harness into a shared `ScrollHarness` found it: the one test that
  builds two harnesses in a single method was closing only the second, because
  each constructor overwrote the field the teardown read.

**Not closed by this**: nested viewports are revealed in the innermost one only,
which is exactly what a hand-wired controller did. Written on `ScrollScope` as
the place it stops telling the truth rather than left to be discovered.

## 3a. `goldberry-web` was not a module, and is built

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| `goldberry-web` is parked, not deferred | a web page on screen | 0441 | **done** — as §9's `web-view`, not as a content module |

**The fifth entry in this run that was wrong about itself**, and the pattern is
now worth naming: every word of it was true, and none of it was about the
question. It said libservo is Rust-only against a deliberately unstable API, so
the module would own a `cdylib` shim and its breakage — correct, and it is why
nothing was built. What it never asked is whether a page needed an engine of this
project's at all.

`webview/webview` is MIT, is one 4500-line header with the implementation in it,
and **brings no engine**: it drives the WebKitGTK, WebView2 or WKWebView already
on the machine. So neither condition ADR-0190 quarantines for — a heavy native
payload, an attribution or copyleft obligation — applies. "Parked" had read like
an answer for two milestones.

**What decided the shape was Wayland, and it took two passes to get right.** The
first draft of the ADR was a companion window aligned to a widget's box, written
before the positioning half was checked. It does not survive: a Wayland client is
not told where it is and may not say where it goes, which is already written into
the SPI — `BackendWindow.position()` returns an `Optional` documented as *"empty
when the platform will not say"*. Reparenting is out for an independent reason
(no cross-process surface adoption). So both ways of making a platform window
look like a widget are closed on the default Linux desktop, and a page is a
**window the application opens**, with `tray-icon`'s exact shape.

**What landed**

- `libgoldberry-webview`, a second shared library built only where WebKit's
  headers are present, linked into nothing and opened on demand. `objdump -p
  libgoldberry.so` shows no GTK or WebKit entry — that one command is what the
  whole separation argument reduces to.
- `natives.webview` (the binding, qualified to `:core`), `render.web` (the SPI,
  the spec, the engine seam), `widgets.shell.web` (`WebPage` and `WebViews`).
- `Capability.WEB_VIEW`, which is the **first capability that is not a bit in
  `libgoldberry`** — it is the presence of the second library, so
  `PlatformCapabilities` gained a two-argument `read` and the enum-parity test
  gained a named exception rather than being deleted.

**Three things worth knowing afterwards**

- **The event loop had to learn to stay awake.** Draining GLib once per iteration
  is not enough: the loop parks in `pumpEvents` for its one-second heartbeat on an
  idle desktop, and nothing wakes it when WebKit has work. A page serviced once a
  second does not scroll. So the wait is capped at 8 ms **while a page is open and
  only then** — the honest fix needs a descriptor from
  `g_main_context_get_poll_func` handed to SDL to wait on, and SDL has no API for
  waiting on somebody else's. Found by reading the loop, not by running it.
- **`webview/webview` 0.12.0 has a bug on its GTK backend.** `set_size_impl`
  applies the size through a complete if/else chain and then falls off the end
  into `return error_info{WEBVIEW_ERROR_INVALID_ARGUMENT, "Invalid hint"}`
  unconditionally — the final `else` is missing. Every resize on Linux succeeds
  and reports failure. The shim checks the hint itself and translates that one
  code; a bogus hint still returns −2.
- **Two GTK majors in one process is a SIGSEGV, and the tray puts one there.**
  The worst of the three and the last found, because it needed the showcase's own
  button pressed: `GdkDisplayManager` is registered by both `gdk-3` and `gdk-4`
  into GObject's process-global type registry, so the second one back gets 0,
  `g_once_init_leave_pointer` asserts, and `gtk_init_check` dereferences NULL.
  SDL's Linux tray is libayatana-appindicator, which links `libgtk-3` — so any
  application showing a `tray-icon` is a GTK 3 process before anybody asks for a
  page, and a web view built on `webkitgtk-6.0` makes it a GTK 4 one. The Linux
  build therefore links **`webkit2gtk-4.1`**, against webview's own preference,
  and the shim additionally checks with `RTLD_NOLOAD` whether the rival major is
  already mapped and declines to open a page rather than killing the process.
  Both probes had passed: neither had a tray, so neither had GTK 3.
- **An ABI check that runs after the binding is not a check.** Found by the same
  crash's clean-up: a stale `libgoldberry-webview.so` left in an install
  directory failed with *"does not export goldberry_webview_gtk_conflict"*
  instead of *"this library is ABI 1 and this build binds ABI 2"*, because
  `WebviewCalls.bind` looked up every symbol and `Downcalls.symbol` threw on the
  first missing name long before the version was read. The probe is bound and
  asked **alone**, first. A version check is only worth writing if it is the
  thing that runs when the version is wrong.
- **An optional feature must not be able to break the call that lists features.**
  The same stale library took `Goldberry.capabilities()` down with it —
  `ExceptionInInitializerError` out of a static initialiser, and then, because a
  poisoned class throws a bare `NoClassDefFoundError` on every later touch, the
  `catch` that handled the first one asked again and got an error with none of
  the cause on it. Binding now answers empty for every failure, and
  `PlatformCapabilities` asks once, outside the `try`.
- **The pump must not touch the library.** It is called once per frame in every
  application that has ever run, and the obvious implementation loads
  `libgoldberry-webview` — and with it GTK and WebKit — on the first frame of a
  process that never asked for a page. An open-page counter is read first, and
  there is a test that calls `pump()` a thousand times to pin it.

**Not closed by this**: Windows and macOS are unverified, in the tray's sense.
The design says SDL's own pump services a `WKWebView` and a WebView2 `HWND`
created on the UI thread, and nothing here has run either.

## 5. The AccessKit bridge is on hold

| Item | Decision | ADR | Status |
|------|----------|-----|--------|
| The AccessKit bridge, and the six entries behind it | not built, no milestone owns it | 0440 | **on hold** |

**Taken today.** Not deferred to a later milestone — that names a date, and
there is none.

The interface was never the difficulty, and the first framing of it here was
wrong: `accesskit_c` is a C API with a cbindgen-generated header covering all
three platform adapters, and it can be had either by driving cargo from CMake
through Corrosion **or** by consuming the project's prebuilt package, which
exists so that toolkit developers need not deal with Rust at all. Both routes
were open.

What decided it is the toolkit's own argument, one level up. Every one of the six
entries refuses to write a constant until something consumes it — *"a role
nothing consumes is a value written for a bridge that does not exist"* — and:

- **nothing has asked.** This joins §12's bucket of work waiting on a consumer
  rather than on a decision;
- **two of its three platforms cannot be run here.** UIA and NSAccessibility sit
  behind the same missing Windows and macOS machines that already block the tray
  on two platforms, the MSVC `.def` and the Mach-O visibility branch. An
  accessibility bridge shipped untested on two thirds of its surface fails
  silently, and fails the people with no other way in;
- **the cost is permanent and lands in `:natives`** — a Rust toolchain on four
  platforms and in CI, or four platforms of vendored prebuilt binaries, which is
  the same licence-and-provenance question PDFium is already parked on.

**Nothing was removed.** `Role`, `Live`, `Semantics` and `SemanticsSweepTest`
stay: the sweep pays for itself today by stopping a focusable widget shipping
with no name, and the data in the tree is what keeps a bridge an adapter rather
than a rearchitecture if it is ever reopened. The six entries keep their prose
and gain an **On hold** paragraph.

**Said plainly where a reader looks**: `README.md` now states that there is no
screen-reader support on any platform and none scheduled, beside the part of
§4's baseline that *is* built and checked — keyboard reachability, focus ring,
WCAG AA contrast, hit targets, reduced motion, 150% text scale.

## 6. What it would have cost the native build, kept for the record

Written before §5 was decided, and kept because a decision to stop is only
readable beside what stopping avoided — and because these are the two rows to
re-read if anybody reopens it.

`docs/ARCHITECTURE.md` §13 named AccessKit and called it "C ABI, fits the FFM
stack". The interface is exactly that — `accesskit_c` is a C API with a
cbindgen-generated header, covering the core data structures and all three
platform adapters, which is one API where the alternative is three.

The build was the part worth deciding, and it is **not** "the superbuild learns
Rust" as first assumed here. There are two ways in, and the project supports both
deliberately:

| | What it costs | What it costs later |
|---|---|---|
| **Build from source** | `accesskit-c` drives cargo from CMake through Corrosion, so `:natives` gains a Rust toolchain on four platforms and in CI. Cross-compiling needs `Rust_CARGO_TARGET` beside the CMake triple | Nothing. One superbuild, one artifact, reproducible from source like every other dependency here |
| **Consume the prebuilt** | Nothing. The project ships a package of header, static and dynamic libraries per platform — in its own words, so that toolkit developers "won't need to deal with Rust at all" — and `find_package(ACCESSKIT)` wires it up | A **vendored prebuilt**, which is the thing `TODO.md` already has open as a licence-and-provenance question for PDFium. Four platforms of somebody else's binaries in the release |

The second row is cheaper today and takes on the debt the first row does not.
It is the same trade PDFium is parked on, so answering it here answers it there.

Everything downstream of that — `Role` gaining `LINK` and the list roles, a trail
becoming a landmark, `Semantics`' value channel and per-cell channel, `isModal`'s
second consumer, a toast being announced — is nine items' worth of work across six
entries, and none of it could start until one of those two rows was picked,
because the shape of the adapter is the shape of what is linked into
`libgoldberry`.

**Neither row was picked. See §5** —
[ADR-0440](../book/src/adr/0440-the-accessibility-bridge-is-on-hold-and-the-semantics-tree-stays.md).

Sources: [accesskit-c](https://github.com/AccessKit/accesskit-c),
[AccessKit](https://github.com/AccessKit/accesskit).

## 7. Two things asked for directly, neither of them on the list

Both came in as questions rather than as entries, and both turned out to be one

### 7.1 A platform library's log line is a log line

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| `(java:…): libayatana-appindicator-WARNING **:` on the console | the platform's own messages routed into SLF4J | 0443 | **done** |

`g_log_default_handler` writing to stderr, from the libayatana-appindicator SDL
loads when `tray-icon` creates a tray. No level, no logger name, not in the log
file — and on the console of an application that configured logging to be
silent, which is the thing [ADR-0023] went to trouble to make possible.

Two bridges. GLib's is `g_log_set_default_handler`, which catches `g_log` and
therefore `g_warning` and its family; SDL's is `SDL_SetLogOutputFunction`. Both
land on `native.<source>.<domain>` — `native.glib.libayatana-appindicator`,
`native.sdl.video` — so an application levels, routes or silences them by name.

The interesting part is the one that is **not** on by default.
`g_log_set_writer_func` catches structured records that a default handler never
sees, and GLib calls `g_error` — which aborts the process — if anything else has
already set one. That is behind `-Dgoldberry.log.glib.writer=true`, for an
application that knows its own process. A toolkit that can kill its host to
redirect a log line has made a bad trade.

Three costs, all recorded in the ADR: three new upcall shapes; one struct
(`GLogField`) laid out by hand and **not** on the layout table, because GLib's
headers are not a superbuild dependency and must not become one; and native ABI
15, since `SDL_LogPriority` and `SDL_LogCategory` are ordinals in enums SDL has
renumbered before.

Verified by running it — the line now arrives as

```text
22:10:21.152 WARN  libayatana-appindicator - libayatana-appindicator is
deprecated. Please use libayatana-appindicator-glib in newly written code.
```

### 7.2 A dialog over a `web-view`

| Item | What it asks for | ADR | Status |
|------|------------------|-----|--------|
| A modal over an embedded page is drawn where nobody can see it | a way to put a dialog in front of a page | 0444 | **done** |

The survey is [`dialog-over-web-view.md`](dialog-over-web-view.md). The finding
that decides it: the page is an X11 **child** of the application's window, so
nothing rasterised into the frame can cover it, and that is not a bug and has no
compositing answer. The only thing that can move is the page.

So it moves. While `Host.isModal()` is true the widget parks its child window
off the parent's corner, by more than its own size, and puts it back afterwards.
Moved rather than resized, because `goldberry_webview_set_bounds` calls
`gtk_window_resize` deliberately and a page parked at 1x1 reflows the document to
one CSS pixel of width. No new export, no C, no ABI bump: it is the call the
widget already makes every frame the box moves.

**Giving the dialog its own popup window was answered rather than deferred**, and
the argument is in the ADR. The short version is that its scrim could not be
translucent on X11, which is the only platform where the problem currently
exists.

The end-to-end behaviour has no automated test and cannot have one — no golden
image can contain a page. What is tested is the arithmetic and the router's
modality; the screen itself is the showcase's web tab, whose javadoc now says
what to look for.

### 7.3 A finding that is not either of those

`SDL_WINDOW_TRANSPARENT` appears to do **nothing** for a non-OpenGL window on
X11. SDL 3.4.14 selects a 32-bit visual only inside
`else if (window->flags & SDL_WINDOW_OPENGL)` (`SDL_x11window.c:601-651`) and
`Sdl3Backend` never sets that flag; the fallback is `displaydata->visual` at
`DefaultDepth`, which has no alpha channel. Wayland honours the flag, which is
consistent with nobody having noticed on a Wayland desktop.

If that reading is right, **every Goldberry menu, dropdown and tooltip has
opaque square corners on an X11 session today**, and `Popup`'s
`frame.fill(0x00000000)` achieves nothing there. It is read off the source and
has not been observed; it is U1 in
[`dialog-over-web-view.md`](dialog-over-web-view.md) §7, it is a screenshot to
confirm, and it is **open**.

## 8. Two more, from looking at the thing that was just built

Both reported against the `web-view` §7.2 landed, and both are defects in it
rather than gaps in the catalog.

### 8.1 The page was white until it had loaded

| Item | ADR | Status |
|------|-----|--------|
| A page shows WebKit's default white from the moment its window is mapped until the document paints | 0445 | **done** |

`goldberry_webview_create_embedded` maps the engine's window and reparents it
inside one call -- which is the order [ADR-0442] requires -- so a window is on
screen over the widget's box before Java has a handle to it. For a page on the
open internet that is several seconds of a white rectangle with nothing saying
why.

A spinner drawn over it would be drawn *underneath* it, which is the premise of
[ADR-0441]. So the mechanism is §7.2's, reused: the page is **opened parked**
and held there until it reports itself loaded, and the `spinner` goes in the box
it will occupy. One new shim export, polled from the painter that was already
calling the shim once a frame; no upcall, no signal, no callback lifetime.

**The first load only.** The first version parked on every load, and the trace
from a real run is what caught it -- GitHub navigates once after settling, and
the tab blanked a second time six seconds in. A browser keeps the old document
up until the new one commits, and so does this now.

Measured on the showcase's web tab: 3.8 s of spinner where there had been 3.8 s
of white.

**Two defects in the first version, both from one line**, and both reported
rather than caught. `open` set the `loading` flag directly instead of through
`setState`: `build` had already run for that frame and nothing asked it to run
again, so no spinner was ever put in the tree -- and the next frame found the
flag already true and skipped the `setState` that was the only thing left to do.
Then, because a `spinner` is what asks for frames for ever, there were no
frames: the loop went idle with the page still parked, and the page appeared
only when a moved pointer caused an unrelated repaint.

The fix is a second field for what has been *asked* for, `Host.repaint()` while
the page is held off rather than leaning on the spinner's animation, and a
`debug` line each time the indicator goes up or comes down -- because that half
is a fact about frames and no test has a frame in it.

### 8.2 Every page left a dead entry in the dock

| Item | ADR | Status |
|------|-----|--------|
| An unclickable window appears in the dock while a page is open | 0446 | **done** |

`goldberry_webview_embed_into` maps the engine's `GtkWindow` while it is still a
toplevel -- it must, because realizing it without mapping leaves the WebKit
widget inside unmapped, which the comment there has recorded since it was
written. For that instant the window manager adopts it; the reparent then takes
it off the root, and the shell is left holding an entry for a window that is now
somebody's child. Nothing can raise, focus or close it.

Fixed by never letting the window manager see it: `override_redirect` set
between realize and map, plus the two EWMH skip hints. Nothing is lost -- it has
no decorations, takes its keyboard from being a child of a window that has
focus, and is positioned by `XReparentWindow`.

Verified on the running showcase rather than argued:

```text
_NET_CLIENT_LIST   0x240003f  "Goldberry -- showcase"     <- and no second entry
page window        0x2800003  Override Redirect State: yes
                              _NET_WM_STATE_SKIP_PAGER, _NET_WM_STATE_SKIP_TASKBAR
```

Webview ABI 4 -> 5 for the two together.

## 9. Three asks against the `web-view`, and one of them had to be designed

### 9.1 A spinner has a size

| Item | ADR | Status |
|------|-----|--------|
| A 16px ring in the middle of a whole tab reads as a decoration, not as the subject | 0447 | **done** |

`spinner size="small|medium|large"`, 12/16/32px. A **value** rather than only a
class, which is `message`'s side of the line `badge` draws -- because a spinner
is a ring, a ring has a stroke, and §8 has no property for the weight of a mark
the painter draws. A large spinner styled only by width and height is a thin
hoop.

The **diameter** stays the stylesheet's: the size puts a class on the node,
`controls.css` gives it a width, and the widget weights the stroke from the
width the cascade actually resolved. One ratio for every size, exactly `2 / 16`
-- so `medium` renders identically to every spinner drawn before this existed
and **no golden moved**.

### 9.2 A page can call back

| Item | ADR | Status |
|------|-----|--------|
| Everything between the toolkit and an embedded page ran one way | 0448 | **done** |

`WebPage.of(url).on("save", arguments -> …)` makes `window.save(…)` a function
the document can call. It is a promise: the handler's return value resolves it,
a thrown exception rejects it with the message. Declared on the **page value**
so the standalone window form gets it for nothing rather than needing a second
mechanism.

Arguments arrive as a JSON array and are **not parsed**. The toolkit ships no
JSON reader and will not add one for a callback; the showcase's demo takes the
quotes off a one-string array and says in as many words that it is not a parser.

One upcall stub serves every binding of every page, keyed by the number handed
over as the callback's `void *arg` -- `SdlFileDialogs`' idiom.

Verified by running, since a real engine needs a library, WebKit and a display
and `WebviewLibraryTest` already draws that line:

```text
DEBUG Webview - web page binds window.goldberrySays()
TRACE Webview - window.goldberrySays() called with ["hello from the page"]
TRACE Webview - window.goldberryFails() called with []
DEBUG Webview - window.goldberryFails() failed; rejecting the page's promise
```

**The ABI guard earned its keep**: the shim went to 6 and the Java constant did
not, and the page refused to open with a message naming both numbers rather than
calling into a mismatched library.

### 9.3 An address bar

| Item | ADR | Status |
|------|-----|--------|
| A page loaded what it was opened with and then nothing could change it | 0449 | **done** |

No new API at all. The widget already took its page as a **value** and nothing
was reading it after the first frame; now it follows it. The application holds
the page it wants, rebuilds, and `web-view` navigates.

Compared with `showsSameAs` -- the url and the document, nothing else -- and not
with `equals`, which §9.2 made unusable: a handler is a lambda, lambdas have no
value equality, and a widget navigating on `equals` would reload for ever.

The spinner comes back for this and **only** for this. A site redirecting itself
must leave the old document up until the new one commits, which is what
[ADR-0445] latched after the first load; an application saying "show this
instead" is a different event, and the widget can tell them apart precisely
because one arrives as a rebuild.

[ADR-0445]: ../book/src/adr/0445-a-page-is-not-shown-before-it-can-be-seen.md

## 10. "The web view is slow on animations" — measured, and not ours

**Open, and not in this repository.** Recorded because the investigation is the
useful part: the next person to ask should not have to repeat it.

### What was measured

The page was made to report its own `requestAnimationFrame` rate and worst frame
gap back through the binding §9.2 added, which is what that mechanism is for.

| Page | Rate | Worst frame gap |
|---|---|---|
| One `transform` animation | 62 fps | 17-25 ms |
| 150 blurred, rotating boxes | **9 fps** | **125 ms** |

So the complaint is real and it is about *heavy* content. A trivial animation is
already at the display's rate.

### It is not the pump, and not `override_redirect`

Both were suspected and both were cleared. The pump drains up to 16 GLib
iterations and the loop is capped at 8 ms while a page is open, so the engine
gets at least 125 turns a second. And reverting [ADR-0446]'s `override_redirect`
— on the theory that an unmanaged window loses its frame clock — changed the
measurement by nothing at all (62 fps either way).

### WebKit has switched hardware acceleration off, by itself

No process in the session maps `libEGL`, a DRI driver or `libgbm`, and none
holds a file descriptor on `/dev/dri/renderD128`. Asking WebKit for
`HARDWARE_ACCELERATION_POLICY_ALWAYS` and reading it back returns **`NEVER`**:
WebKit has decided this machine cannot accelerate and pinned it.

The machine is an NVIDIA proprietary driver. WebKitGTK 2.52's renderer wants a
GBM device and the proprietary stack does not offer one the way Mesa does. The
documented workaround, `WEBKIT_DISABLE_DMABUF_RENDERER=1`, is a no-op on 2.52 —
tried, still `NEVER`.

### The control that settles it

A **plain 20-line GTK application** embedding the same WebKit, with no Goldberry
in the process, behaves identically: no EGL, no DRI fd, policy `NEVER`. Whatever
this is, it is not the embedding.

`WEBKIT_FORCE_COMPOSITING_MODE=1` was also tried, in the shim, and changed
nothing. It was taken back out rather than shipped.

### Why nothing was built

A `hardware-acceleration-policy` knob on `WebPage` is the obvious thing to add
and was **not** added: it cannot be shown to help anywhere from this machine,
because WebKit overrides it here. Shipping an API whose only evidence is that it
compiles is the dead weight the export list's own rule names. The finding is in
`WebView`'s javadoc instead, where somebody hitting it will look.

[ADR-0446]: ../book/src/adr/0446-an-embedded-page-is-never-the-window-managers.md

### 10a. The knobs, measured

Asked for other workarounds, so every environment switch WebKit 2.52 has was
tried against the same heavy page, in the **standalone control** — no Goldberry
in the process, so the numbers are WebKit's alone:

| | fps |
|---|---|
| baseline | 11.8 / 11.8 / 12.5 |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | 12.3 / 11.9 / 10.9 |
| `WEBKIT_DMABUF_RENDERER_DISABLE_GBM=1` | 11.0 / 11.0 / 9.6 |
| `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` | 13.4 / 13.2 / 13.0 |
| `WEBKIT_SKIA_ENABLE_CPU_RENDERING=1` | 13.4 / 10.4 / 8.2 |
| `WEBKIT_WEB_RENDER_DEVICE_FILE=<render node>` | no change |

All inside the noise. That `SKIA_ENABLE_CPU_RENDERING` matches the baseline is
the tell: the baseline **is** CPU rendering.

Two further checks, both negative, both worth not repeating:

- The system is not at fault. A `dlopen` probe of `gbm_create_device` +
  `eglGetPlatformDisplay(EGL_PLATFORM_GBM_KHR)` + `eglInitialize` on
  `/dev/dri/renderD128` answers **OK, EGL 1.5, vendor NVIDIA**, and a GTK3
  `gdk_window_create_gl_context` realises under both backends. GL works; WebKit
  declines to use it.
- `webkitgtk-6.0` is installed and is the **same 2.52.6**, so the GTK4 pairing
  ADR-0441 rejected for the tray would not have bought a newer engine anyway.

One dead end recorded so nobody reads it as evidence: WebGL's
`UNMASKED_RENDERER_WEBGL` reports `Apple GPU` here. That is WebKit's
**fingerprinting-resistant spoof**, not a renderer, and it says nothing about
acceleration either way.

### 10b. What actually moves the number

Not the usual web advice, because the usual advice addresses a compositor that
is switched off:

| Change to the page | fps |
|---|---|
| 150 animated boxes with `blur(1px)` | 13.2 / 13.1 / 13.0 |
| the same, filter removed | 12.9 / 13.3 / 11.5 |
| the same, `will-change: transform` | 13.0 / 12.4 / 12.8 |
| **40 animated boxes** instead of 150 | **23.8 / 23.3 / 29.0** |

`will-change` is a hint to a GPU compositor and buys nothing without one; the
filter was not the cost either. **Animated area is the cost**, because software
rasterisation is paid in pixels. That is the advice to give an application whose
embedded page feels slow.
