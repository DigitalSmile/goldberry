# The whole open list, read once and sorted

Working notes for the batch that started on 2026-09-19, when the instruction was
"fix them all" against `book/src/TODO.md`.

The list's open half — everything above `## Answered` — holds about ninety
entries. **They are not the same kind of thing**, and the first work of this
batch was to say which kind each one is, because a list where "waiting on a
GitHub Release tag" sits beside "the cascade could be faster" cannot be worked
top to bottom.

Status legend, as in [`todo-sweep.md`](todo-sweep.md): **done** means code, tests
and ADR have landed. **in progress** means it is being built now. **open** means
not started. **answered** means decided not to build, with the reason recorded.
**blocked** means the thing it waits on is not in this repository.

### `masonry`'s missing row

The entry's own diagnosis was that nothing blocked the mechanism — §5's
spec-then-metrics-then-gallery gate simply had nothing to have passed, because
`masonry` **has no row in `docs/core-widgets.md` at all**. That row is written now,
in §1 beside `row`, `column` and `stack`, with a §3 metrics row beside
`panel`/`card`. Three things in it are decisions rather than description:

- **`columns` and `min-column-width` are exclusive**, and a `masonry` given both is
  a build-time error rather than a precedence rule nobody remembers.
- **The width it counts against is its own, read last frame** — the same door
  ADR-0196 opened. Safe for ADR-0117's third rule because a column count changes
  the wall's *height* and not its width, and therefore safe **only for a `masonry`
  whose width comes from its parent**. A `masonry` inside a shrink-to-fit box would
  oscillate, and the row says so rather than leaving it to be discovered.
- **`min-column-width: 320`** is the default, and the leftover from an uneven
  division goes to the gaps rather than to one wider column.

## 16. Wave two, and one entry answered by measurement

Thirteen actionable entries were left after wave one. Six agents took twelve of
them; the thirteenth is the natives jar, which the parent took because it needed
an experiment rather than an opinion.

**ADR-0438 answers it rather than building it.** The entry offered two fixes — a
Gradle plugin *or* module-metadata variants keyed on OS and architecture — and the
second one does not work. Measured in a throwaway producer/consumer build:

- a plain JVM consumer **silently resolves the unattributed jar**, because a
  variant is chosen by matching the *consumer's* attributes and an ordinary
  `java-library` declares no operating system;
- a consumer that *does* declare one **fails with an ambiguity**, because a
  variant missing an attribute is compatible with every value of it, so the shared
  `runtimeElements` ties with the platform-specific variant.

The three ways out of that tie — attributing the shared bindings jar, deleting the
unattributed variant, or a disambiguation rule — are all the consumer's, the last
one literally so: disambiguation rules are registered on the consumer's
`attributesSchema`. **A producer cannot close this entry at all.** A Gradle plugin
is the whole answer, which is what JavaFX, LWJGL and sqlite-jdbc each ship, and it
is a new published artifact on a chain that has never run — so it is a decision
for after the first release.

What landed instead is the correction, and a documentation fix worth having: the
snippet in `docs/releasing.md` now adds **all four classifiers**, since
`NativeLibrary` picks at run time and the one-platform form is the one that fails
quietly for somebody building on macOS for an application that ships to Linux.

**Marked "not scheduled" rather than open**: *markup cannot name a painter*. Its
own text says "nothing has needed it: every consumer so far is a chart widget
written in Java", which puts it with the clipboard watcher and the primary
selection in §12 — waiting on a consumer, not on a decision.


## 17. Wave two, integrated

**Thirty-three ADRs, 0406–0438**, contiguous. Twelve more entries left the open
list, and one was narrowed by measurement rather than closed.

**Two spec rows written for this batch turned out to be wrong**, and both were
caught by the agent implementing against them rather than by review:

- `core-widgets.md` said a `masonry` in a shrink-to-fit parent "would oscillate,
  and that combination is refused". It does not oscillate — `flex-basis: 0`
  columns make the wall measure zero — and it is not refusable there, because
  shrink-to-fit is the *parent's* property.
- `design-system.md` §3 said `masonry` gap `16 (12)`; `controls.css` says `12`
  flat at both densities.

**What integration found that no single agent could.** Each worked from master,
so none saw the others' changes:

- `ShowcaseDocumentsTest` counted two readers of one property where there are
  four, because `slider` became stateful and its CSS type moved to the node the
  state builds. The walk follows that now.
- The 150% ratchet reported five accepted overruns that **no longer happen** —
  `masonry`'s responsive columns gave the narrow Basic screen's button rows room.
  Deleted, which is the ratchet working: an exception that stops being needed is
  reported as loudly as a new failure.
- `:widgets:javadoc` went red on `[#localPart()]` in `Slider`, which moved to
  `SliderControl` — ADR-0405's doclint gate catching exactly what it was
  installed for.

**Thirty-eight goldens moved.** Twelve are the shadow knock-out and every one of
those is the anti-aliased arc of a rounded corner; the rest are the slider's new
edge, the narrow Basic screen's reflow, and the gallery screens that carry cards.
Each was looked at before it was blessed.
