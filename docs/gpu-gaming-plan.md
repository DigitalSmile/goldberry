# GPU for games: ray tracing and the settings around it — implementation plan

Written 2026-10-25, before any code. `:gpu` draws a `canvas3d` well enough for
a lit cube; this plan covers what a game asks of it after that. That means ray
tracing first, and then the settings a game's options screen has: present mode
and frame cap, render scale and upscaling, anti-aliasing, anisotropy and HDR
output. It follows `gpu-plan.md`'s shape: what was found, the decisions with a
status, phases with exit criteria, risks, and a log.

Each decision becomes an ADR when it is taken, parked in `docs/snapshot/adr/`.
**D3 was taken on 2026-10-25: option (b), a Vulkan device of the toolkit's own
(ADR-0666), and with it D1 changed to ray-tracing pipelines.** The hardware
tier (phase 4) is built and tested, with scene updates, compaction and a
packed shadow mask (ADR-0667), and its CI lane runs on the x64 leg (lavapipe
at 128-bit vectors is refused, ADR-0668). **Phase 1 is done** (ADR-0669):
native ABI 26 binds the SDL_GPU calls a game needs, and `:gpu` has indirect
draws, a stencil test, constant blending and GPU-to-GPU copies. **Phase 2 is
done** (ADR-0670): a window's present mode and frame cap change at run time,
the `hud` shows them, and `GpuDevice.features()` answers what a device can do.
**Phase 5 is done** (ADR-0671): `canvas3d` draws at a render scale and
upscales bilinearly or with FSR 1, through `dev.goldberry.gpu.upscale`.
**Phase 7 is done** (ADR-0672, ADR-0673): the ray tracer traces a pixel's
lighting, occlusion and reflection included, and the showcase's GPU screen has
a ray-traced room with a game's graphics settings. Open: phase 3 (the software
tier, and the panel's Software segment with it) and phase 6 (HDR, waiting for
a display). The next free ADR number is 0674.

## 2. What this plan delivers

1. **What a device can do, asked for, never assumed.** `GpuDevice.features()`
   answers with a `GpuFeatures` record: ray tracing (none, software, hardware),
   indirect draws, sample counts, anisotropy, HDR output. Anything a game turns
   on is checked against it first.
2. **The SDL_GPU features that are bound nowhere yet**: indirect draws and
   dispatches, stencil reference, blend constants, texture and buffer copies,
   compute samplers and vertex storage textures.
3. **Ray tracing everywhere, in software.** A two-level bounding volume
   hierarchy (BVH) built in Java and traversed by an HLSL include in the
   application's compute shaders. It runs on every SDL_GPU driver (Metal, D3D12,
   Vulkan, lavapipe) through the compute passes that exist today.
4. **Ray tracing in hardware, on Vulkan**, behind the same HLSL include, once
   phase 0 has measured what reaching the device costs (D3).
5. **Game settings**: present mode and frame cap changed at run time, a
   `canvas3d` render scale with an upscaler (bilinear, or AMD FSR 1's EASU and
   RCAS, built as fragment passes), and an optional HDR10 swapchain.
6. **A showcase chapter** with a ray-traced scene (shadows, reflections, ambient
   occlusion) and a settings panel that switches all of it live.

**Not in this plan**, so it is not rediscovered:

- ray-tracing *pipelines* (raygen, hit and miss shaders, shader binding tables); D1 says why;
- mesh shaders and variable-rate shading: SDL_GPU has neither, and the two devices here disagree on which they have;
- GPU timestamp queries: SDL has none, so frame times stay CPU-side, as the `hud` measures them today;
- DLSS, XeSS and FSR 2/3: proprietary SDKs, or temporal upscalers that need motion vectors from the renderer;
- a game engine: scene graphs, materials and asset loading stay the application's. The toolkit gives the queries and the settings.

## 3. Decisions

Marked **proposed** until phase 0 or the user takes them.

### D1. Rays are traced by inline ray queries from compute shaders (proposed; changed by D3)

**Changed with D3 (ADR-0666):** on a device of the toolkit's own, the hardware
tier uses **ray-tracing pipelines** (`trace.lib.hlsl`: ray generation, two
misses, one closest-hit group). The argument below was that ray queries fit
SDL's compute passes; on our own device nothing has to, and pipelines run on
the GTX 1660 Ti, which has no ray queries. The software tier (D2) still means
compute shaders on SDL's device, and keeps its include.

There are two ways to trace rays:

- **Ray queries**: `RayQuery` in HLSL (DXR 1.1), `VK_KHR_ray_query`, Metal's `intersector`. Called from any shader, in compute in practice.
- **Ray-tracing pipelines**: separate raygen, hit and miss shaders with a binding table.

Ray queries go into the compute passes `:gpu` already has, they are the one
model all three APIs share, and they cover what a game uses rays for: shadows,
reflections, ambient occlusion and picking. A pipeline would need a fourth kind
of pipeline, a binding table and a dispatch SDL_GPU does not have.

The cost is this machine: the 1660 Ti has pipelines and no ray queries, so it
runs the software tier (D2). It has no RT cores either, so its pipelines run on
the shader cores, as the software tier does. Phase 0 measures how far apart
the two are on it.

### D2. Software first: a BVH built in Java, traversed in HLSL (proposed)

- **Bottom level (BLAS)**: one per mesh, built once from its triangles with a binned surface-area heuristic, and refitted (bounds only) when a skinned mesh moves.
- **Top level (TLAS)**: over instances (mesh and 3×4 transform, mask, id), rebuilt every frame on the CPU; its cost for a few thousand instances is in phase 0's benchmark.
- **On the GPU**: three storage buffers (nodes, triangles, instances), bound by `ComputePass.bindAccelerationStructure`, and traversed by `goldberry/raytrace.hlsli`: `gb::traceClosest`, `gb::traceAny` (for shadows), and a hit record with instance id, primitive id, barycentrics and distance.
- **The include is the API.** It reads the same with the hardware tier (D3): `GB_RAYTRACE_HARDWARE` switches its body to `RayQuery<…>`, so an application writes one shader and compiles it twice.
- **Tested exactly**: a Java traversal of the same BVH is the reference, and the GPU's hit ids and primitive ids must match it ray for ray, as the Y'CbCr shaders match `YuvConversion` (ADR-0477).

### D3. How the hardware tier reaches the device (decided 2026-10-25: (b), ADR-0666)

The user chose **(b)**, keeping the FFmpeg work's "no SDL patch" rule. The
analysis that led there is kept below.

Three ways, and each costs something:

| | (a) A small SDL patch | (b) A second Vulkan device | (c) Wait for upstream |
|-|-----------------------|----------------------------|-----------------------|
| What | `SDL_GPUVulkanOptions` turns on `rayQuery`, `accelerationStructure` and `bufferDeviceAddress`. The patch adds read-only properties for the `VkInstance`, `VkPhysicalDevice`, `VkDevice`, queue and family, and a texture's or buffer's `VkImage`/`VkBuffer`. Acceleration structures are built on our own command buffers on SDL's queue, on the device's one thread. The shader gets each structure's device address in a uniform and turns it into a handle with `OpConvertUToAccelerationStructureKHR`, so SDL's descriptor layout does not change | `:media`'s generated bindings moved to `:natives` as `natives.vulkan` (exported to `:media` and `:gpu`), plus a device of our own that traces into its own image, which is copied back through host memory into an SDL texture | Nothing until SDL_GPU has ray tracing |
| Cost | A patch rebased on every SDL bump (phase 6b's precedent, and its risk row). Keeping in step with SDL's image layouts | Two copies through the host every frame (about 8 MB each way at 1080p), two devices' memory, and a frame of latency | No hardware ray tracing |
| Platforms | Vulkan (Linux, Windows). D3D12 and Metal would need the same patch for their own devices | Vulkan only; it cannot help Metal | – |

**Recommended: (a)**, once phase 0's spike shows SDL still creates its device
with the features on, and that a structure built outside SDL is read by an
SDL-made compute pipeline on lavapipe. Against it: the FFmpeg phase-4 work
chose "no SDL patch" (staged planes instead), and this would be the first patch
applied to SDL. If the user keeps that rule, (b) is the fallback: hardware rays
behind a copy-back, worth it only where tracing costs more than the copies,
which phase 0 measures. Either way D3D12 and Metal stay on the software tier
until there is a patch or upstream support.

### D4. Ray tracing is a capability with three answers (proposed)

**Built with phase 4 (ADR-0666)** as two answers, `Unavailable(reason)` and
`Hardware(device)`; `Software` joins when phase 3 does. The mode has `OFF`,
`AUTO` and `HARDWARE` until then. **Changed with phase 2 (ADR-0670):**
`GpuDevice.features()` does not carry it. `RayTracer.availability()` stays the
one answer, because it opens a Vulkan device on first ask and its package
already depends on `dev.goldberry.gpu`.

```java
public sealed interface RayTracing permits RayTracing.None, RayTracing.Software, RayTracing.Hardware {
    record None(String reason) implements RayTracing {}
    record Software() implements RayTracing {}
    record Hardware(String api, boolean positionFetch) implements RayTracing {}
}
```

`GpuDevice.features().rayTracing()` answers. An application asks with a
`RayTracingMode` (`OFF`, `AUTO`, `SOFTWARE`, `HARDWARE`), and
`AccelerationStructure.build(device, scene, mode)` refuses `HARDWARE` where the
device answers otherwise, naming the reason, as `createShader` names a missing
format. `goldberry.gpu.raytracing=off|software|auto` overrides it, as
`goldberry.gpu` does for the GPU itself.

### D5. Settings are the renderer's, present mode is the window's (proposed)

- **The window's**: present mode (`VSYNC`, `MAILBOX`, `IMMEDIATE`) and a frame cap, both changed at run time through `SDL_SetGPUSwapchainParameters` and `FramePacer`, and HDR output (D6). These are the `PresentMode` enum `gpu-plan.md` deferred to "its consumer", which a settings screen is. Where the window presents on the CPU, the setting is kept and does nothing, and the window says so.
- **The canvas's**: `canvas3d render-scale=0.5..2 upscale=linear|fsr1`. The renderer draws into a target of the scaled size, and the layer upscales it into the box before the composite.
- **The renderer's**: MSAA, anisotropy, ray-tracing mode, shadow resolution. A `GraphicsSettings` record with withers is a convenience the showcase uses; the toolkit does not apply it, because only the renderer knows its passes.

### D6. HDR output is an option, not the default (to measure)

`SDL_WindowSupportsGPUSwapchainComposition` and the `HDR10_ST2084` and
`HDR_EXTENDED_LINEAR` compositions exist in SDL 3.4. The UI texture is SDR
BGRA, so a window in HDR draws its UI at SDR white (203 nits for PQ, BT.2408)
and a canvas's scene above it. `ToneMapping` already has PQ and the gamuts.
Phase 6 measures it on a display that has HDR. Without one it stays out.

## 5. Risks

| Risk | Mitigation |
|------|------------|
| The 1660 Ti cannot test hardware ray queries | Lavapipe can, and the GPU lane runs it. Parity tests compare the two tiers, so the software tier tested here vouches for the include |
| The runners' Mesa has no lavapipe ray tracing | Phase 0 finds out. If it has none, the hardware tier's tests are skipped there and required locally on lavapipe, as `goldberry.gpu.required` does for the device. **It has (Snapshot 76), but arm64's lavapipe crashes building a scene at its 128-bit vectors, so it is refused (ADR-0668) and the tests are required on x64 alone** |
| SDL changes its image layouts or queue use under a patched handle | Our command buffers only build acceleration structures, which are buffers; SDL images are never touched outside SDL. A test drives a build between two SDL submits |
| Software traversal too slow for 1080p on integrated GPUs | Render scale (phase 5) and a ray budget per pixel are the answer; the benchmark tells the guide what to promise |
| MSL ray queries through SPIRV-Cross are incomplete | Metal stays on the software tier, whose include is plain compute |
| The BVH builder becomes a hot path for animated scenes | Refit instead of rebuild; TLAS only per frame; the builder's cost in the benchmark source set |
